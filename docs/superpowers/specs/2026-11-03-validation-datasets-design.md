# Validation datasets: raw event logs in, organized tables out

**Status:** draft, 2026-11-03
**Builds on:** [Spider2 reference datasets](2026-10-30-spider2-reference-datasets-design.md) (13 projects, exact round trips) and the six `datagen` examples.

## Why

The product turns raw event logs into organized tables. To validate it we need test datasets that any data processor can consume, whether DuckDB, Spark, Flink or a stream processor, and whose correct output is known. We then run every processor on the same data, compare each processor's tables with the known answer and with the other processors' tables, and benchmark them.

The project's principle is that **everything comes from logs.** A dataset's input is a single ordered event log, like a Kafka topic, and nothing else. Lookup and dimension data come from events in that log too. A customer row comes from the customer's sign-up event; a product row comes from its "product added" event. The output is a set of organized tables: dimensions, normalized facts and, for some datasets, partitioned tables.

- **Spider2 datasets:** the output is known, because it is the 13 projects' source tables. The events were worked out backwards from those tables.
- **Synthetic datasets:** the events are generated by `datagen`. A reference build (SQL) turns them into dimension and fact tables, and those tables are the expected output.

The raw log carries more than the tables: extra ids and event attributes. Getting from raw to organized is the job each processor is tested on.

## Goals

1. **One dataset contract.** Every dataset has the same parts:
   - an ordered JSON-payload event log;
   - an event schema;
   - expected result tables;
   - a manifest;
   - a context file.

   Spider2 and synthetic datasets have identical structure.
2. **Events only.** All 13 Spider2 datasets are re-cut so that entities arrive as events. The rebuilt tables must still equal the source exactly.
3. **Dimension and fact tables for the six synthetic projects,** produced by a reference build from their logs.
4. **Data by name.** Data files live under one central data root, and the repo refers to them only by name, so the root can later be S3 or a network file system without changing any reference.
5. **Self-explanatory datasets.** Each dataset's context file says:
   - what the raw data is;
   - how it was made or extracted;
   - what the expected output is;
   - how to regenerate it;
   - how to extend it, with more data or new features.
6. **Engine runners and a benchmark harness.** DuckDB, Spark, Flink (batch) and Flink streaming over a Redpanda topic each read the log, build the tables and are checked against the expected tables. All of them run locally. The harness compares engines and records timings.

## Non-goals

- Uploading to S3 or serving from a network file system. Only the local root is implemented now; the naming must make the others a configuration change.
- Stage 2 of the Spider2 work, where packs *generate* realistic logs. That stays a separate effort.
- Porting every dataset to every engine in this effort. See [Engines](#engines).
- Per-key partitioned Kafka topics. The log is one totally ordered partition.
- Committing Parquet or any other data to git.

## Anti-goals

These would make the effort a failure even if every test passed:

- **A table that enters the log as a table.** If an engine needs a side input other than the log to build the results, the dataset breaks the principle.
- **Expected outputs that only DuckDB can read or produce.** The contract is meant to be engine-neutral; DuckDB is just the reference implementation.
- **Invented values.** A Spider2 dataset's events must not contain values that are not in the source, except times given by a documented rule, as in batch 1 and 2.
- **A rebuilt Spider2 table that no longer equals its source.** The exact round trip that passes today must still pass after the re-cut.

## Terms

| Term | Meaning |
|---|---|
| **dataset** | One named, versioned unit: log + schema + expected results + manifest, with a recipe and a context file in the repo |
| **log** | The input: every event of the dataset in one total order, as Parquet with a JSON payload column |
| **results** | The expected output tables, as Parquet |
| **recipe** | What makes the dataset: Spider2 ingest SQL, or a `datagen` project, profile and seed |
| **reference build** | The SQL that turns the log into the results (DuckDB). It defines the expected tables for synthetic datasets, and proves them for Spider2 ones |
| **engine run** | One engine building the results from the log, written to a run folder and compared |
| **data root** | Where data files live: `NEORISK_DATA_ROOT`, default `<repo>/data/datasets` |

## The dataset contract

### Names and the data root

A data file is named `<dataset>/<version>/<path>`, for example `olist/v1/log/part-00000.parquet`, and resolved against the data root:

```text
name:   olist/v1/log/part-00000.parquet
local:  $NEORISK_DATA_ROOT/olist/v1/log/part-00000.parquet     (default ./data/datasets/…)
later:  s3://<bucket>/datasets/olist/v1/log/part-00000.parquet   (same name, other root)
```

- Dataset names are kebab or snake case and match the repo folder name.
- Versions are `v1`, `v2` and so on. A version, once built and recorded, is immutable. Changing the log, the schema or the results makes a new version. Changing the context file does not.
- All code resolves names through one function, so adding a remote root later touches one place.

### On the data root

```text
<dataset>/<version>/
  manifest.json            name, version, recipe revision, source sha256, counts, every file's sha256 + rows
  schema/events.json       one entry per event type: its payload fields, their types, nullability, refs, docs
  log/part-NNNNN.parquet   the event log in seq order; parts are consecutive ranges of seq
  results/<table>.parquet  expected output tables (or results/<table>/ with hive partitions)
  expected/…               other expected outputs (see per kind below)
```

### The log

There is one Parquet table per dataset. Its rows are in `seq` order, and `seq` is the total order of the log. A stream processor replays it front to back; a batch engine sorts by `seq`. Either way, both see the same history.

| Column | Type | Meaning |
|---|---|---|
| `seq` | int64, unique, from 1 | The total order (event time, then simkit's tie rules, as today) |
| `event_time` | timestamp(µs, UTC) | When the event happened |
| `event_type` | string | e.g. `customer_signed_up`, `order_placed` |
| `entity_type` | string | The owner's entity type, e.g. `customers` |
| `entity_key` | string | The owner's key, as text. This is the natural Kafka message key |
| `schema_version` | int32 | The event schema's version, from `schema/events.json` |
| `payload` | string (JSON object) | The event's own attributes |

Envelope rules:
- The envelope repeats nothing from the payload except what a stream processor needs in order to route and key messages.
- Simkit's internal columns (`event_id`, `partition_id`, `cause_id`, `action_id`) go in the payload when an event has them, so no information is lost.

Payload JSON rules. Together they keep the round trip exact:

- **Encoding:** the payload is a UTF-8 JSON object, and text is carried byte for byte. This is the same encoding as `datagen replay`'s messages (`neorisk_simkit.replay.encode`), and the log reuses that code.
- **Integers:** 64-bit integers (ids, keys, money in minor units) are written as JSON **strings**, as `replay` does by default. Some JSON readers lose precision above 2⁵³.
- **Timestamps:** ISO-8601 UTC text with microseconds, such as `2017-10-02T10:56:33.000000Z`.
- **Floats:** true floats (`f64`) are written as JSON numbers in their shortest form that reads back exactly.
- **Nulls:** missing values are JSON `null`. `null`, `""` and `"\N"` stay three different values.
- **Schema file:** each event type's field list and types are in `schema/events.json`, so no engine has to infer types from the JSON.

The log is written in parts of a fixed number of rows, like topic segments. The part size is left to the builder.

### Entities as events

This rule is the same for Spider2 and synthetic datasets, and is applied when the log is written:

- **Creation:** every entity row becomes one `<entity>_created` event, named for the entity, for example `customers_created`, or a domain name the recipe gives, such as `customer_signed_up`. It is stamped at the row's `created_at`, keyed by the entity, and carries the entity's attributes, `ext_id` included.
- **Snapshot-only attributes:** some attributes are known only as their value at the snapshot, such as a product's current stock, a `last_update` stamp or a lifetime total. The recipe marks those columns as **snapshot** columns. They leave the creation event and travel in one `<entity>_snapshot` event at the dataset's snapshot time N. That way no event carries a value from its future.
- **Classifying columns:** which columns are snapshot columns is a per-dataset research call. Each one is listed, with its reason, in the context file. When in doubt, a column is a snapshot column.
- **Refs:** a ref in any payload holds the target entity's key, the same key as in the target's `entity_key`.

So the results' dimension tables are built from creation and snapshot events, exactly as the fact tables are built from business events.

### Results and expected outputs

- **Spider2:** `results/` holds every source table, written from the SQLite source. `expected/queries/<id>.parquet` holds each saved query's answer on the source.
  - **Column types:** each results column has one Parquet type, taken from the column's declared SQLite affinity: INTEGER → int64, REAL/NUMERIC/DECIMAL → float64, and the rest → string.
  - **Mixed columns:** a column whose stored values don't fit that type is written as **string**, holding SQLite's `CAST(x AS TEXT)`, with NULL kept as null. Examples are `''` in an INTEGER column, or a text value in a DECIMAL column. Such a column is listed as `mixed` in `dataset.toml` and in `CONTEXT.md`, and `build.sql` must produce the same text.
  - **Mixed integer and real values:** a DECIMAL column holding 62 and 62.7 fits float64 and is not mixed. *(My call.)*
- **Synthetic:** `results/` holds the tables of the dataset's three designs (see [Synthetic table designs](#synthetic-table-designs)). `expected/` holds:
  - the ground truth from `datagen`: `labels.parquet`, the golden features where the pack has them, and the cases;
  - `check.json`, the `datagen check` report on the run;
  - `questions/<id>.parquet`, each question's answer from simkit's own tables.

  Labels and golden data are never in the log, because they are what a model should not see.
- **Partitioned tables:** a results table may be partitioned (hive style, e.g. `results/fact_payments/event_date=2026-01-03/…`), and `dataset.toml` says so.
- **Comparison:** each table compares as a **multiset of rows**. The rule is the same for every engine:
  - **Numbers:** integer and float cells compare by value, so 62 equals 62.0, as `refdata compare` does today.
  - **Text:** compares byte for byte.
  - **Nulls:** null equals only null.
  - **Tolerance:** the only one is 1e-9 relative, on columns that are true floats (`f64`, or REAL in the source).
- **Saved queries:** `dataset verify` runs each one. It loads the results tables built from the log into an in-memory SQLite database, as `refdata compare` does now, runs the query, and compares the answer with `expected/queries/`. Engine runs are graded on tables only. The queries are a check on the dataset, not engine work. *(My call.)*

## Tooling

A new app, **`apps/dataset`**, with CLI **`dataset`**. `refdata`'s `fetch`, `ingest`, `rebuild` and `compare` keep working on the new paths. The new app adds:

| Command | Does |
|---|---|
| `dataset list` | The catalogue: name, kind, version, built locally or not, and which engines pass |
| `dataset build <name> [--force]` | Run the recipe, then write the log, schema, results, expected outputs and manifest under the data root. The output must match the version's lock file (see below) |
| `dataset verify <name>` | Run the reference build (DuckDB) over the log and compare with `results/` and `expected/`; exit 1 on any difference |
| `dataset resolve <name/version/path>` | Print where a name lives under the current root |
| `dataset run <name> --engine duckdb\|spark\|flink\|flink-stream` | One engine run into `$NEORISK_DATA_ROOT/_runs/<name>/<version>/<engine>/<run-id>/`, then compare and record metrics |
| `dataset bench [names…] [--engines …]` | Every requested engine on every requested dataset, then one comparison report (JSON + HTML) |

`dataset build` for a Spider2 dataset is: `refdata ingest`, then write the log, then `dataset verify`. The exact round trip becomes **source tables = reference build over the log**, and the existing `test_project_<p>.py` tests switch to that form. For a synthetic dataset, `build` is: `datagen run`, then write the log, then the reference build, which writes the results.

**There is one pipeline, not two** *(my call)*:
- `refdata ingest` keeps producing the simkit-layout dataset as an internal stage, so `datagen check` and Spider2 stage 2 keep working on it.
- `pack.py` keeps declaring entities as entities.
- Turning entities into events is done only by the **log writer**: entity rows become `<entity>_created` and `<entity>_snapshot` events, and business event tables become events.
- `views.sql` is deleted; `refdata rebuild` runs `build.sql` over the log; `refdata compare` is unchanged.
- The same log writer serves synthetic datasets, from a `datagen run` directory.

**Versions are recorded in git** *(my call)*:
- `datasets/<name>/<version>.lock.json` is committed. It holds every file's name, sha256 and row count, plus the recipe revision and the source sha256.
- `dataset build` checks its output against the lock and fails on any difference. Changed output needs a new version; there is no overwrite of a recorded version.
- Builds must therefore be deterministic: the same pinned `uv.lock`, fixed writer settings and a stable sort.
- `--force` only rebuilds local files that are missing or corrupt. Matching the lock is still required.
- `dataset list` reports "built locally" when the local files match the lock.

Synthetic datasets also get a second check that does not depend on the reference build:
- every dimension table must equal the corresponding simkit entity table;
- every transaction fact table must equal a projection of the corresponding simkit event table;

with the column mappings declared in `dataset.toml`. That way the synthetic results are not graded only against themselves.

## Engines

All of these run on the laptop (macOS, 14 cores, 36 GB, Java 17, Docker).

| Engine id | How | Reads |
|---|---|---|
| `duckdb` | in-process, `build.sql` (the reference) | log Parquet |
| `spark` | PySpark, local mode | log Parquet; payload parsed with `from_json` using `schema/events.json` |
| `flink` | Flink SQL, batch mode, in Docker | log Parquet |
| `flink-stream` | Flink SQL, streaming mode, in Docker, reading a Redpanda topic | the log replayed into one topic in `seq` order, keyed by `entity_key` |

- **The Redpanda topic** is filled with the existing Kafka sink of `datagen replay`, or a thin variant of it. The message key is `entity_key` and the value is the envelope plus payload.
- **Streaming results:** the job keeps the result tables up to date as a changelog. When the topic is drained, the harness folds the changelog into final tables and compares them.
- **Docker:** one `docker compose` file brings up Redpanda and Flink for local runs.
- **Metrics per run:**
  - wall time, split into load, build and write where the engine allows;
  - peak memory;
  - events per second;
  - for each table: pass or fail, the row count, and a sample of differing rows.

**Scope of ports:** porting `build.sql` to Spark SQL and Flink SQL by hand is the largest cost here. In this effort four datasets get every engine:

| Dataset | Why |
|---|---|
| `pizzarunner` | small, quick to debug |
| `sakila` | mid-sized, many entities |
| `olist` | the largest real dataset, about 1.5M rows |
| `payments` | synthetic |

All 19 datasets run on `duckdb`. Adding a port to another dataset is an "extend" recipe in `datasets/README.md`.

Exact text formatting is part of what is tested. If an engine cannot produce a source table's exact text, such as a float printed in SQLite's style, that table fails on that engine and the report says so. The expected tables are not loosened to fit an engine.

## Synthetic table designs

By the user's decision of 2026-11-06, each synthetic dataset is modeled **three ways**, picked from the designs compared in the *Beyond Facts & Dimensions* atlas (2026-10-19). Each design is a separate reference build over the same log, so one dataset tests a processor on three shapes of output. A star schema stays in every dataset, because it is the Kimball design this spec asked for and the one the simkit check grades directly.

| Dataset | Designs | Why these |
|---|---|---|
| `ecommerce` | `star`, `dv`, `an` | Users move region: SCD2, satellites and per-attribute history all have work to do |
| `payments` | `star`, `dv`, `obt` | An auditable money lifecycle; one wide payment row is the ML-feature shape |
| `payments_subscriptions` | `star`, `act`, `an` | A subscriber's lifecycle is a customer journey, the activity schema's home ground |
| `crypto_exchange` | `star`, `dv`, `obt` | A trade links two orders and two traders; a wide trade row is the analyst shape |
| `layer1` | `star`, `act`, `obt` | Accounts form an activity stream; a wide transaction row joins receipt and inclusion |
| `social` | `star`, `dv`, `act` | The follow graph is links; engagement is a stream |

The design ids and their rules:

| Id | Design | Tables | History |
|---|---|---|---|
| `star` | Star schema (Kimball) | `star_dim_<entity>`, `star_fact_<process>` (no calendar dimension: every star dimension is checked against a simkit table, so dates stay columns) | SCD2 (`<entity>_sk`, `valid_from`, `valid_to`, `is_current`) for entities whose attributes change in the log; facts point at the version in force at event time. An accumulating snapshot fact where a lifecycle exists |
| `dv` | Data Vault 2.0 | `dv_hub_<entity>`, `dv_link_<relation>`, `dv_sat_<parent>_<group>` | Hash keys are `md5` of the business key as text; insert-only; a satellite row only when its `hashdiff` changes; load time is the event time |
| `an` | Anchor modeling | `an_<entity>` (identity), `an_<entity>_<attribute>`, `an_<e1>_<role>_<e2>` (ties) | One row per attribute change, with `changed_at` |
| `act` | Activity schema | `act_<entity>_stream`, optionally `act_<entity>` | One row per activity: `activity_id`, `ts`, `customer`, `activity`, `feature_1..3`, `revenue_impact`, `link`, `activity_occurrence`, `activity_repeated_at` |
| `obt` | One big table | `obt_<grain>` | One wide row per fact grain, every attribute bound as of the fact's time |

- **Layout:** `specs/<design>.sql` holds one design's `-- table:` blocks, and every table name starts with `<design>_`. *(This replaces the single `build.sql` for synthetic datasets, so each design is one engine port.)*
- **Column types:** int32, int64, float64, string, bool, date and timestamp(µs, UTC). Anything else, such as DuckDB's HUGEINT from a `sum`, fails the build.
- **Questions:** each dataset has three, in `specs/questions/<id>/`. `oracle.sql` answers it from simkit's own tables, never the log, and its answer is `expected/questions/<id>.parquet`. Every design answers it from its own tables only, in `<design>.sql`, and must give the oracle's answer. At least one question per dataset depends on history or lifecycle.
- **The simkit check:** `[[check]]` entries in `dataset.toml` map a results table's columns (optionally filtered) to a simkit table's columns. Every star dimension and transaction fact has at least one entry. The check runs at build time, when the simkit run is at hand.

- There is one pipeline. `refdata ingest` stays as the internal stage, the log writer turns entities into events, and `views.sql` becomes `build.sql` over the log.
- Versions are recorded by committed lock files, and builds must reproduce them exactly. In PR 1, entities already enter as creation events; PR 2 adds snapshot events and records `v1`.

## Left to the builder

- **File details:** the log's part size, Parquet writer settings and row-group size.
- **Synthetic table design:** each project's dimension and fact tables (grain, names, which are partitioned), following the Kimball guidance in `docs/research/event-based-systems.md`.
- **Naming:** domain names for entity creation events, where a natural one exists (`customer_signed_up` and so on).
- **Software versions:** Flink, Redpanda and PySpark, chosen for Java 17 and Python 3.12.
- **Engine internals:** how the Flink streaming job writes its changelog, and how the harness folds it.
- **The report:** its HTML layout.
