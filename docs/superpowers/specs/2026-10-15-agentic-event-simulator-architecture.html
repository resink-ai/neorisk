Architecture design · neorisk base

Agentic Event Simulator

A repo-native library and CLI where an AI agent turns a short business brief into a simulation pack, and the engine turns that pack into large volumes of realistic, checked event data. Owners and shards talk only through immutable, latency-bounded requests; mutable state has exactly one owner; one total order drives both execution and replay; every resource an action needs is reserved at once; and memory is bounded by workers, not actors.

Status final design Date 2026-10-16 Builds on 5 research notes in docs/research/

01Decisions

FormOne library (simkit) and one CLI (datagen)No services, no UI, nothing over a network. Agents author in the repo; humans review PRs and one report.
VocabularyFive primitives: Table, Process, Action, Source, CheckLedgers, handoffs, holds, concentration and overlays are standard-library recipes.

02Requirements

Fast

10⁷ events end to end in about a minute; 10⁸ ordinary events in ≤ 10 minutes warm on one 16-core, 64 GB machine. Shard-heavy workloads have their own budget.

Simple

One library, one CLI, three core commands. Nothing calls anything over a network.

Expressive

E-commerce, payments, exchanges, L1 chains and social networks fit five primitives. A distinct user group is an overlay, not a fork.

Easy to modify

Adding an event, behavior or user group is a small, local change reviewed in an ordinary PR.

Easy to verify

Declared domain laws are checked on every row; realism is measured on weighted, unit-appropriate samples.

Easy to understand

One compact report: counts, linkages, transitions, concentration, rejections, cohorts, interference, checks.

03System overview

A pack is a Python module that loads into a small normalized plan. The engine advances simulated time in frontier steps. Within a step it alternates parallel owner execution and ordered shard processing in rounds until nothing below the step's end remains. It then merges the step's output into canonical order and streams it through cross-owner enrichment, checks and the Parquet writer.

Two ways to define a process

Handwritten kernel S1

Any behavior; typed config

  • A Numba function using the ABI in 05, parameterized by a typed config dataclass
  • S1's shopper journey and KYC; permanently matching, the L1 envelope, cascades

State machine M3

Common behavior; no code

  • A table-driven interpreter with closed semantics, built after two handwritten kernels show the common shape
  • Calls actions through a generated, inspectable dispatch module

def define(p: Pack, execution_owner="payment_id") -> None:
    payment = p.table("payment", cols={"amount": i64, "captured": i64, "refunded": i64,
                                       "refund_hold": i64, "status": cat})
    fees    = p.accumulator("platform_fees", i64)        # additive; no decision reads it

    pay = p.machine("payment", owner=execution_owner, initial="authorized",
                    start=p.on_created("payment"))
    pay.state("authorized",
        branch={"captured": (0.93, dist.lognormal(median_s=3600), std.capture(fee_to=fees)),
                "otherwise": (0.07, None, None)},
        timer={"expired": "7d"})                            # earliest wins; leaving cancels
    pay.state("captured",
        repeat=(dist.exp(mean_days=9), 0.04, std.refund(budget=std.remaining("captured", "refunded"))),
        max_repeats=3, spawn={"dispute": (0.006, dist.gamma(mean_days=21))})

    p.check("chk.refund_budget", law.sum_le("refund.amount", "payment.captured", by="payment_id"),
            required=True)

05Action interface

Every action, built-in or custom, follows one native calling convention: validate, reserve every resource it might use, then commit. Nothing after a successful reserve can fail.

examples/payments/specs/kernels.py (simplified)

@kernel(state="payment", max=Res(records={"refund": 1}, timers=1))
def partial_refund(ctx, s, cmd, out):
    left = s.captured - s.refunded - s.refund_hold      # s: this partition's row view
    if left <= 0:
        return reject(R_NOTHING_REFUNDABLE)             # 1. validate: no writes
    if not out.reserve(records={"refund": 1}, timers=1):
        return RETRY                                   # 2. runtime swaps slabs, re-invokes
    amt = std.checked_min(left, ctx.rng.lognormal_minor(site=1, median=2500))
    s.refunded = std.checked_add(s.refunded, amt)      # 3. commit: cannot fail
    out.emit_refund(ctx.t, payment=ctx.self_id, amount=amt)
    out.timer(ctx.t + DAY, T_SETTLE_REFUND)
    return COMMIT

The contract

  1. Reservation vector.reserve takes counts for every resource: records per event table, created rows per table, timer-heap entries, outbound requests and messages. Each kernel declares its maxima (max=Res(…)); the runtime checks the vector against the worker's slabs and pools in one call. reject and RETRY are legal only before the first write; debug mode snapshots the row and fails the run otherwise.
  2. Retries are invisible.RETRY means the runtime swaps in a fresh slab and re-invokes the same command. Random draws are keyed by (seed, instance, action, occurrence, site, k), where k counts draws at one site within an invocation and occurrence advances only on commit or reject, so a retry replays identical draws.
  3. Fixed fan-out sub-steps.An action whose fan-out is unbounded declares a constant sub-step size (for example, 64 fills). It processes at most that many, stores a cursor, and schedules a same-time continuation at the top priority, so no other command at that timestamp interleaves. Results never depend on buffer capacity. All-or-nothing variants (fill-or-kill) run a read-only preflight before the first fill.
  4. Composition.a.then(b) is two atomic actions. An atomic composite is one kernel.
  5. Typed generated emitters.out.emit_<event>, out.create_<table>, out.timer and out.request are generated per schema and write into slabs. create returns a provisional handle usable immediately within the step (12).
  6. Restricted views; trusted code.Kernels get a row view of their own partition's state and read-only arrays for shared inputs; Numba refuses to compile writes to read-only arrays. Kernels are still trusted, reviewed code. A lint flags mutable module globals. Debug mode runs compiled with bounds checking, and arithmetic on amounts uses checked helpers, so overflow behaves the same compiled and uncompiled.
  7. Delivery and lateness.A timer or message addressed to a retired instance is detected by slot generation, dropped, and counted as late_messages in the manifest.
S1 exit test, native ABI proof: a compiled kernel that emits several record types, creates rows, schedules timers and requests, and rejects. It runs under forced exhaustion of each resource in turn, compiled with checked mode and uncompiled, and must produce identical logical output.

06Execution model

Partitions and boundaries

  • Every piece of mutable state has exactly one partition. An owner partition holds one user, payment or campaign with all its processes. A shard partition holds one order book, chain, inventory group or bonus pool with its own processes.
  • Partitions interact only through immutable messages. An owner sends a request to a shard and waits for a response. The payload is copied (cart lines, amounts, a limit value), never aliased.
  • Every boundary declares a minimum latency δ > 0: the platform's response time, for example 200 ms for checkout. Responses arrive at t_request + latency, with latency ≥ δ sampled from a declared distribution. Shard-emitted records (order accepted, sale recorded) carry the shard's true decision time.
  • Joint constraints use holds. If a decision needs both owner and shard state (spend from a wallet and take a unit of stock), the owner first places a hold on its own state, the shard decides on its own, and the owner then commits or releases the hold. No decision ever reads stale or shared mutable state.
  • Multi-shard decisions use reservations, never merging. A cart with three SKUs in three inventory shards sends three reserve requests, joins on the responses, then commits all or releases all. Reservations carry a TTL, so a shard frees units if the commit never arrives. Shards stay small; nothing spreads transitively.
  • Owner-to-owner messages (an inviter credited when an invitee qualifies) are allowed only when the target doesn't act on them within the step: they're delivered at the next step boundary or later. Anything tighter means the two belong to one owner (a campaign, a household).
  • Creating an owner (checkout creates a payment) is a creation message. The new owner starts at its creation time in the next round of the same step.

Rounds within a frontier step

flowchart TD
  A["Step starts: T to T+step"] --> B["Owners run ahead in parallel
until step end or first request"]
  B --> C["Shards process requests with
time below horizon H, in canonical order"]
  C --> D["Deliver responses and creations
resume or start owners"]
  D --> E{"Anything left
below T+step?"}
  E -->|yes| B
  E -->|no| F["Seal step: merge, enrich, check, write"]
  • Run ahead. Each runnable owner executes its events in order until it reaches the step end or issues a request, at which point the whole owner suspends.
  • Safe horizon. H = min(step end, min over suspended owners of (their request time + δ)). A suspended owner can't act before its response arrives, which is at least δ after its request, and an owner that reached the step end issues nothing more in this step. So every request with time < H is already known. The shard processes all of them in canonical order.
  • Progress. Because δ > 0, the earliest outstanding request is always below H, so every round makes progress. There are no blocking waits and no cross-thread calls.
  • Cost. Rounds per step ≈ the longest chain of request/response hops any owner makes within the step, usually a handful. Small rounds run single-threaded to avoid parallel launch overhead.
  • Calendar queue. Partitions are kept in time buckets by next event time, so a step visits only partitions with work in it. No step scans all owners.
  • Spawn bounds. Each process declares max_spawn_depth (default 3), and each step has a max_admissions limit. Exceeding either fails the run with a diagnostic naming the process.
  • Step closure. A step seals only when no owner is runnable below the step end, no request below the step end is pending, and no creation is unadmitted.
  • Shard-internal processes. Matching, block building and pool accounting run inside their shard, which executes its own heap in canonical order. Requests enter that heap as commands.

One total order

  • Execution: each partition pops commands by (time, priority, cause_lamport, seq). Scheduled times must be ≥ the current time; validation and runtime enforce it.
  • Lamport clocks are assigned at commit: lamport = max(partition_clock, cause_lamport) + 1, where partition_clock is one counter for the whole partition, shards included. So within a partition, commit order and Lamport order are identical, even when a high-priority command runs first.
  • Replay: the canonical key is (event_time, lamport, partition_id, seq). Within a partition it reproduces execution order. Across partitions, a response always has a larger clock and a later time than its request. Independent partitions are ordered by the deterministic partition_id.
  • Same-time precedence is declared as command priority before execution: messages before timers by default, continuations first. KYC declares redemption at exactly the expiry instant as expired.
  • The S1 tests include priority inversion (a high-priority credit and a low-priority debit at the same time) and equal-key commands from different partitions.

08Behavior overlays

An overlay adds a configurable group of actors with distinct behavior to an existing pack, without editing it, and makes them emit the same event schema as everyone else.

examples/ecommerce/specs/overlays/bounty_hunters.py

def apply(o: Overlay, size=300, zombies=dist.negbinom(mean=12, disp=0.5),
          share_device=0.7, arrive=dist.burst(start="day 10", span="30d"),
          qualify_timeout="14d"):
    camp = o.cohort("bounty_hunter", table="user", size=size, arrivals=arrive,
                    execution_owner="campaign_id",      # hunter + zombies = one owner
                    suppress=["shopper_journey"])

    h = o.machine("hunter", members=camp, initial="new")
    h.state("new", branch={"inviting": (1.0, dist.lognormal(median_s=900),
             o.base.signup.then(std.spawn_members("zombie", n=zombies, via=o.base.invite,
                 refs={"device": std.share_with_parent(share_device)})))})
    h.state("inviting", join={"collecting": ("zombie_paid", "all_spawned")},
            timer={"collecting": qualify_timeout}, late="count")
    h.state("collecting", repeat=(dist.exp(mean_s=60), 1.0, o.base.claim_inviter_bonus),
            until=std.no_unclaimed("zombie_paid"), then="gone")

    z = o.machine("zombie", members=camp.spawned("zombie"), initial="invited")
    z.state("invited", branch={"ordered": (0.85, dist.lognormal(median_s=600),
             o.base.signup_via_invite.then(o.base.first_order.with_params(
                 amount=std.near("referral.min_order", above=0.05)))),
             "otherwise": (0.15, None, None)})
    z.state("ordered", request={"paid": o.base.claim_invitee_bonus},  # pool shard if capped
            on_reject="gone")
    z.state("paid", branch={"gone": (1.0, dist.exp(mean_s=300), std.send_parent("zombie_paid"))})

    o.label(camp, role={"hunter", "zombie"}, outcome=("attempted", "qualified", "paid"),
            available_at=std.after("paid", dist.gamma(mean_days=30)))

Benchmark workloads

  • Workloads are committed, runnable files: benchmarks/s1.toml, s2.toml and s2_pool.toml. Each fixes seed, actors, operation mix as shares of proposals, arrival schedules, live-owner curve, timer populations, postings per event, payload columns, skew, and overlay settings.

  • S2: 20M users, 30M payments, 10⁸ exported events, 2.5 postings per payment event, 90-day dispute timers, one hot SKU group taking 5% of checkouts.
  • S2-pool: a global capped bonus pool that every referral claim reaches, with the bounty-hunter overlay at 1% of users.
  • Accounting: exported events, histories, cases, snapshots, postings and labels are counted separately. Timing runs from engine start with a warm JIT cache to manifest.json written; cold compile is timed separately. Numba plus Polars threads are capped at 16.
  • Also verified: identical logical records across 1, 4 and 16 threads, two slab sizes and two step lengths.

Memory model

Every item has a hard cap enforced at runtime and an expected size estimated by validate. A run whose caps exceed the machine budget is refused up front; a run that hits a cap fails with the item named. v1 has no spilling.

Enrichment in the right order

  • Owner-local values (static attributes, the owner's own history) attach inside kernels by gather or per-reader cursor.
  • Cross-owner features (device-level rolling counts across users) run only after a step seals, over the step's output merged into canonical order. Reducers carry ring-buffer state across steps. A feature for event e counts only events with event_time strictly earlier than e, so simultaneous events never leak. The merge sort is part of the benchmark.
  • Fast measurements (battery, signal) are sampled at observation time. The scorer is fitted once on a sample, frozen, and applied per step.

12Identity & reproducibility

Identity

  1. Provisional handles within a step.create returns (partition, local ordinal), flagged provisional, usable immediately for messages and references in the same step.
  2. Dense indices at step close.New rows of each table get dense indices by prefix sum over partitions in partition_id order, then local ordinal. In-step references are remapped before writing. Dense indices back all arrays, bitsets and reducers.
  3. Public IDs by keyed permutation.Exported IDs are a seeded Feistel permutation of (table, dense index) into 63 bits, so they fit a signed BIGINT. They are collision-free by construction and look random.
  4. Slots and generations.Live state rows are slots, distinct from entity identity. Each slot carries a generation that is bumped on reuse, so timers or messages for a retired instance are detected and dropped.

13Output layout

A run writes a directory of Parquet files, not one file. Each event type gets its own typed table, split into one file per frontier step. Every file is sorted by the canonical key, so any set of files merges back into the exact global order with a streaming k-way merge.

ChoiceWhy
One table per event typeEach type has its own typed columns: no sparse wide table, no JSON payload column, and a direct mapping to one SQL table and one Kafka schema each (14)
One file per stepThe writer streams each sealed step straight to disk, so memory stays bounded by the step cap. Step boundaries are deterministic, so files are byte-identical across runs. Workers write different types in parallel
date= directoriesHive-style partitioning that DuckDB, Polars, Spark, Trino and BigQuery external tables read natively, with date pruning
Step indexLets replay jump to the first, last or any time range of events by reading one small file instead of scanning the dataset
Writer settings fixedzstd level 3, 128k-row groups, dictionary encoding for categories, statistics on event_time and IDs. Pinned in the manifest because they affect bytes
  • Common columns, first in every event table: event_id, event_type, event_time (timestamp µs UTC), lamport, partition_id, seq, cause_id, action_id. Type-specific columns follow.
  • Sizes: S1's workload has 10⁷ events at about 120 B/row raw, roughly 0.4 GB on disk. S2's has 10⁸ events, about 4–5 GB, with steps of about 1M rows giving files of 10–60 MB per type.
  • One file when you want it: datagen export examples/ecommerce/out/full-s42 --single-file all.parquet compacts everything into one canonically ordered file. It uses a unified schema: common columns, plus every type's columns, nullable. Good for small samples and notebooks; not the default, because it serializes the write.
  • Amounts are int64 at a declared per-asset quantum, exported as decimal128(38,0) base units where needed. Legacy adapter: datagen export --legacy-fraud writes today's events.parquet / golden.parquet / meta.json for bench.

15Replay & sinks

datagen replay reads a finished dataset and streams a chosen slice of events, in canonical order, to one or more sinks. It never reruns the simulation; it only reads Parquet. It is part of the same CLI, and sinks are small classes in io/sinks/, so there is still no service to run.

$ datagen replay examples/ecommerce/out/full-s42 --first 100                       # default sink: stdout, one JSON object per line
$ datagen replay examples/ecommerce/out/full-s42 --last 100 --sink file:last100.json?format=json-array
$ datagen replay examples/ecommerce/out/full-s42 --first 10000 \
      --sink kafka://localhost:9092/ecom.{event_type}?key=user_id&format=avro
$ datagen replay examples/ecommerce/out/full-s42 --from 2026-03-01 --to 2026-03-02 \
      --types order_placed,payment_captured --pace x3600 --rebase now \
      --sink kafka://broker:9092/ecom.events --sink stdout:?format=table   # tee to two sinks

Selecting events

Filters combine first, then --first / --last apply to what is left. Order is always canonical, (event_time, lamport, partition_id, seq), so a replay of the whole dataset equals the order the engine executed.

Sink URIFormatsBehavior

  • Message shape: one flat object per event: the common columns, then that type's columns. IDs and amounts are JSON strings by default, because 63-bit integers exceed JavaScript's safe range and amounts must not lose precision; --numbers emits them as numbers. Timestamps are RFC 3339 with microseconds.
    {"event_id":"5823061146093315521","event_type":"order_placed","event_time":"2026-03-01T09:14:02.381220Z","lamport":"88213","user_id":"…","quantity":2,"amount":"4599","channel":"app","coupon_code":null}
  • Pacing: --pace asap (default) sends as fast as the sink takes; --pace realtime or x60 maps simulated gaps to wall-clock gaps; --rate 5000/s caps throughput. --rebase now shifts every timestamp so the first event is at the current time, keeping all gaps; useful when consumers or Kafka retention expect fresh data.
  • Labels: excluded by default. --with-labels adds a label_available event for each label at its label_available_at, so a downstream system sees labels arrive late, as in production. Golden columns are never replayed.
  • Delivery and resume: at-least-once. Kafka and file sinks write .replay-state.json with the last acknowledged canonical key; --resume continues from it. Consumers can deduplicate by event_id. --dry-run prints the plan, row count and estimated duration without sending.
  • Exit report: rows read and sent per sink, rate, first and last canonical key, and errors. Exit code is non-zero if any sink failed.

class Sink(Protocol):                       # io/sinks/base.py — the whole extension surface
    def open(self, schema: Schema, opts: SinkOptions) -> None: ...
    def write(self, batch: pa.RecordBatch) -> None: ...   # canonical order, ≤ 64k rows
    def checkpoint(self) -> CanonicalKey | None: ...        # last key known delivered
    def close(self) -> SinkReport: ...
  • The reader works in Arrow record batches end to end; memory is bounded by one step per open type plus the batch size, whatever the replay length.
  • A new sink (S3, Postgres COPY, Pub/Sub, HTTP) is one class registered by URI scheme. Kafka support is an optional extra, neorisk-simkit[kafka] (confluent-kafka), so the base install stays small.
  • Throughput (planning estimates): stdout/file JSON 0.5–1M events/s; Parquet file several million/s; local Kafka 100–300k msgs/s with batching (linger.ms=20, 1 MB batches), bounded by the broker. --pace and --rate slow it down, never speed it up.

  • A one-line CODEOWNERS rule requires someone other than the author to approve changes to expectations.yaml or checks/domains/.
  • CI generates the report for the PR head SHA. Required checks fail CI if missing, inconclusive or unanchored.
  • validate reports structural contradictions only: cross-partition writes, δ = 0 boundaries, unbounded spawns, caps over budget. It never claims stochastic feasibility. sweep is deferred.
  • Agent tooling: examples/AGENTS.md, one authoring guide, and five worked projects with overlays in examples/.

A pack lives in a project folder: the reviewed spec plus three folders that datagen fills. Every command takes the folder. The repo ships five worked projects in examples/: ecommerce, payments, crypto_exchange, layer1 and social.

19Non-goals & risks

Not in v1

  • Services, UI, distributed execution, spilling
  • Live LLM agents at runtime
  • Expression languages; a general compiler
  • Zero-latency cross-partition interaction
  • sweep and approval machinery
  • EVM, consensus, mempool; settlement netting
  • Ingestion delay and retroactive corrections (except label availability)

Remaining risks

  • Throughput is unmeasured. Mitigation: committed workloads and per-item run stats from S1.
  • Minimum latency is a modeling choice. Responses always take at least δ. Mitigation: δ is a realistic platform latency, and same-partition interactions remain instantaneous.
  • Hot shards serialize. A global pool or chain runs one loop. Mitigation: the S2-pool workload measures it; shard sizes are reported.
  • Many rounds per step if owners chain many requests. Mitigation: small rounds run single-threaded; rounds per step are reported.
  • Numba constrains kernels and kernels are trusted. Mitigation: std covers common actions; checked compiled debug mode; review.
  • The size estimate may still be low. Mitigation: recalibrate after S1 before committing to M3+.
