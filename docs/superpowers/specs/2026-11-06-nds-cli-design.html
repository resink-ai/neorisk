nds: NeoRisk Data Storage

MVP design for a small, Git-like CLI that stores large datasets outside Git and keeps them reachable from the repo. 2026-11-06 · shipped in PR #21 (local and ssh remotes, multi-dataset config)

In one paragraph. Each dataset folder gets an nds.yaml. It names one or more remotes and says which files to include/exclude. nds push walks the folder, fingerprints each file cheaply, moves it to the remote, and leaves a symlink in its place. Nothing in your code or notebooks changes. If the remote already has the same path with different content, nds stops and asks. Two remotes ship: local folder (move + symlink) and ssh (one batched rsync per dataset, local files kept). S3 and MCP slot in later behind the same interface.

1. Why

The repo's data/ folder is already 6.2 GB and is git-ignored (Spider2, eth, refdata, …). Those files are expensive to rebuild, but today they exist in exactly one place: this laptop. We want a cheap way to park them somewhere safe, such as ~/data now and the desktop or S3 later, without losing the ability to open them from the repo path.

4. The config file

One nds.yaml per dataset folder. Plain YAML, easy to review in a PR (the data is ignored by Git, but this file is committed).

# data/spider2/nds.yaml
dataset: spider2              # name used as the folder on the remote
default_remote: home

remotes:
  home:
    type: local
    path: ~/data              # files land in ~/data/spider2/...
  # later:
  # lake:
  #   type: s3
  #   url: s3://neorisk-data/datasets
  # desktop:
  #   type: ssh
  #   host: my-desktop
  #   path: /data/data

include: ["**/*"]
exclude:
  - "cache/**"
  - "**/*.tmp"
  - "splits/**"               # derived, rebuildable
  - "nds.yaml"
ADDED Many datasets, one file. An nds.yaml may carry a datasets: map (name → path, include, exclude). Each dataset gets its own remote folder and manifest. Use nds push <name> or nds push --all; the remote is chosen with -r. See apps/nds/README.md.

5. Fast fingerprint (no full read)

You asked for a quick hash that avoids reading the whole file. Options:

OptionCost on a 5 GB fileCatchesNotes
size + mtime only~0Most editsmtime changes on copy, so it is useless across machines.
size + sampled hash
(head, middle, tail 1 MiB, blake2b)		~3 MB read, millisecondsSize changes, edits to the sampled regionsRecommended. Stdlib only, same value on any machine.
Full xxHash / MD5Full read, seconds to minutesEverythingOffered as --full when you want certainty.
TRADE-OFF A same-size edit that lands only between the sampled regions is not detected by the default fingerprint. For immutable datasets this is fine. --full is the escape hatch, and the fingerprint records which mode produced it.

6. Push, step by step

Step 3 outcomes

Not on remote
Move it.
On remote, same fingerprint
Skip the transfer. Just replace the local file with a symlink.
On remote, different fingerprint
CONFLICT Prompt [o]verwrite / [s]kip / [a]bort. Non-interactive runs abort unless --force or --no-clobber.

Safety rule: the local original is replaced by the symlink only after the copy exists on the remote at the right size. A crash mid-push leaves either the original or a verified copy, never neither. Re-running push is safe.

7. Remote interface (so S3 / SSH fit later)

Every backend implements four calls. The MVP implements them for a local folder; the rest of the CLI never knows the difference.

class Remote(Protocol):
    def list(self, dataset) -> dict[path, Entry]   # path, size, fingerprint
    def stat(self, dataset, path) -> Entry | None
    def put(self, local_file, dataset, path) -> None
    def get(self, dataset, path, local_file) -> None

The remote keeps an append-only .nds-manifest.jsonl (one line per file, later lines win) beside the data, so ls-remote and conflict checks never re-read files. Appending, not rewriting, keeps a 174k-file dataset fast, and the local remote writes the line before it makes the symlink, so a crash never loses a moved file. The ssh remote keeps the manifest in memory and writes it once, atomically, at the end of a push.

Local vs. real remotes. A local remote moves and symlinks, since it is the same machine. S3 and SSH remotes copy and leave the local files in place, because a symlink to S3 is not possible. The YAML type decides which behaviour applies.

Gotcha worth knowing: symlinks write through

After a push, writing to data/spider2/orders.parquet edits the stored copy directly. Nothing is "staged". nds status therefore compares each symlinked file against the manifest and reports modified when they differ. For read-mostly datasets this is acceptable; making stored files read-only (chmod a-w) is a cheap option if you want protection.

8. Deliberately out of the MVP

  • S3 and MCP backends (interface is ready; add one per PR).
  • Versions or history: a push replaces, there is no log or rollback.
  • Dedup across datasets, compression, encryption.
  • Parallel transfers and resumable uploads.
  • Locking for two machines pushing at once.
  • gc for orphaned files on the remote.

9. Build

  • New app apps/nds, Python 3.12, console script nds, joining the uv workspace like apps/dataset.
  • Dependencies: pyyaml (already in the lockfile) plus stdlib argparse, hashlib, fnmatch/pathlib. No new third-party packages for the MVP.
  • Tests with pytest on tmp_path: push/skip/conflict/crash-safety/exclude/pull.
  • Size: roughly 800 lines of source with the ssh remote and multi-dataset config. Real run: data/, 175,293 files (about 5 GB), pushed to ~/data and to a desktop over ssh in a few minutes.

  • Pull in MVP? You did not mention it, but without it a fresh clone cannot get its links back. I included a minimal version.
  • Remote location. Default ~/data, as you described. Should nds init create it if it is missing?
