nds: NeoRisk Data Storage

A small, Git-like CLI that stores large datasets outside Git and keeps them reachable from the repo. Final build, as merged in PRs #21–#23 (2026-11-06 to 2026-11-10).

In one paragraph. One nds.yaml (in data/, or one per dataset folder) names remotes and says which files to include/exclude, and may list many datasets. nds push walks a dataset, fingerprints each file cheaply, and sends it to the remote. For a local remote it moves the file and leaves a symlink in its place, so nothing in your code changes. For an ssh remote it copies with one batched rsync and leaves the local files alone. If the remote already has the same path with different content, nds stops and asks. Re-running is safe. S3 and MCP remotes are not built; they slot in behind the same remote interface.

1. Why

The repo's data/ folder is already 6.2 GB and is git-ignored (Spider2, eth, refdata, …). Those files are expensive to rebuild, but they used to exist in exactly one place: this laptop. nds parks them somewhere safe (~/data and a second machine over ssh) without losing the ability to open them from the repo path.

RESULT First real run: 5 datasets under data/ (eth, datasets, ref, spider2, spider2-meta), 175,293 files, about 5 GB. Pushed to the desktop over ssh in about 2 minutes, then moved into ~/data in about 100 seconds. status shows every file stored on both remotes, and a full SHA-256 of the largest file matched on both machines. datasets/_runs (benchmark scratch) was excluded.

4. The config file

One nds.yaml can manage many datasets. This is the real data/nds.yaml (host and paths shown as placeholders). The file lives in data/, which is git-ignored, so it is not committed; keep a copy if you want it under version control.

default_remote: home
remotes:
  home:    {type: local, path: ~/data}                          # move + symlink back
  desktop: {type: ssh, host: my-desktop, path: /data/neorisk}   # rsync copy, local files stay
exclude: ["**/.DS_Store", "*.tmp", "*.lock", "*.wal", "*-journal"]   # shared by every dataset
datasets:
  spider2-meta: {path: spider2-meta}
  ref:          {path: ref}
  spider2:      {path: spider2}
  eth:          {path: eth}
  datasets:     {path: datasets, exclude: ["_runs/**"]}   # adds to the shared excludes
  • Each dataset gets its own remote folder (~/data/spider2/...) and its own manifest.
  • A dataset's include replaces the shared one; its exclude adds to the shared one. Exclude wins. A pattern with no / matches the file name anywhere, like .gitignore.
  • Dataset paths must be relative, inside the config's folder, and must not overlap.
  • A folder with its own nds.yaml is a separate dataset and is skipped by a parent-level run.
  • Without a datasets: section the file describes just its own folder (dataset: names it; default is the folder name), and nds push needs no name.
  • The remote is chosen with -r (default default_remote).

5. Fast fingerprint (no full read)

You asked for a quick hash that avoids reading the whole file. Options:

OptionCost on a 5 GB fileCatchesNotes
size + mtime only~0Most editsmtime changes on copy, so it is useless across machines.
size + sampled hash
(head, middle, tail 1 MiB, blake2b)		~3 MB read, millisecondsSize changes, edits to the sampled regionsRecommended. Stdlib only, same value on any machine.
Full xxHash / MD5Full read, seconds to minutesEverythingOffered as --full when you want certainty.
TRADE-OFF A same-size edit that lands only between the sampled regions is not detected by the default fingerprint (a test shows --full catches it). Files up to 3 MiB are read in full either way. The fingerprint records its mode (s: or f:), and a comparison uses the mode the manifest was written in, so mixed runs still agree.

Two kinds of remote

localssh
TransferRename into the store (same disk, instant), else copy and check the size. A file only appears at its final name once complete.One rsync -aL --files-from per dataset. rsync writes each file under a temporary name and renames it when complete.
Local file afterwardsA symlink to the stored copy, swapped in atomically.Untouched. Symlinks are followed, so a file already parked locally is copied from its store.
ManifestOne line appended per file, before the symlink is made.Held in memory and written once, atomically, at the end of the push.
Re-runStored files are skipped; a changed local copy is a conflict.Same. A crash before the manifest is written just means those files are re-checked.

Crash safety, honestly: nothing is ever deleted before a copy exists at the remote. On a local remote a file is renamed into the store, then recorded, then linked, so a crash in that short window can leave a file stored but not yet linked back (or stored but not yet recorded). The data is safe in the store; nds pull restores the link when it was recorded. Making that window self-healing is future work.

7. Remote interface (so S3 fits later)

A remote is a small class. The CLI only talks to this surface, and a links_back flag says whether push moves and symlinks (local) or copies (ssh).

class LocalRemote:   links_back = True
    list() -> dict[rel, Entry]      # size + fingerprint, from the manifest
    record(rel, entry)              # append one manifest line
    flush()                         # no-op
    put(local, rel)                 # move into the store

class SshRemote:     links_back = False
    list() / record() / flush()     # manifest cached in memory, written once at flush
    put_many(root, rels)            # one batched rsync
    get_many(root, rels)            # one batched rsync back (pull)

Each dataset folder on the remote holds an append-only .nds-manifest.jsonl: one JSON line per file (rel, size, fp), later lines win, and a torn last line from a crash is ignored. Appending instead of rewriting keeps a 174k-file dataset fast (the first design rewrote the whole manifest per file). Because the manifest has everything, ls-remote and conflict checks never re-read the data.

Gotcha worth knowing: symlinks write through

After a push, writing to data/spider2/orders.parquet edits the stored copy directly. Nothing is "staged". nds status therefore compares each symlinked file against the manifest and reports modified when they differ. For read-mostly datasets this is acceptable; making stored files read-only (chmod a-w) is a cheap option if you want protection.

8. Deliberately out of the MVP

  • S3 and MCP backends (the remote classes are the extension point; add one per PR).
  • Versions or history: a push replaces, there is no log or rollback.
  • Dedup across datasets, compression, encryption.
  • Parallel transfers and resumable uploads.
  • Locking for two machines pushing at once.
  • gc for orphaned files on the remote.
  • Self-healing for the crash window on a local push (section 6), and a per-file hash check after an ssh copy beyond what rsync does.
  • Keeping nds.yaml under version control when it lives in a git-ignored folder.

9. Build

  • apps/nds, Python 3.12, console script nds, a member of the uv workspace. Run it with uv run --package nds nds -C data push --all -r desktop.
  • Dependencies: pyyaml (already in the lockfile) plus the standard library. It shells out to ssh and rsync for the ssh remote.
  • About 730 lines of source (cli, config, fingerprint, ops, remote) and 17 pytest tests on tmp_path. They cover push, idempotence, conflicts, edits through a symlink, pull, include/exclude, the sampled-vs-full fingerprint, nested datasets, multi-dataset config, and an ssh round trip through a fake ssh.
