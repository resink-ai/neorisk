# music (Spider 2.0-lite): the Chinook database under its upstream names

Source: `data/spider2/music.sqlite` (1.0 MB), opened read-only. It is compared with `data/spider2/chinook.sqlite`, which is already the `chinook` dataset (`datasets/chinook/`, research in `chinook.md`).

Every number below comes from one of these scripts in `scripts/music/`:
- `c1_equivalence.py`: table-by-table row multisets, column names, declared types and storage classes, under the contract's comparison and a strict typed one;
- `c2_rowid_order.py`: physical row order, system tables, indexes;
- `c3_ingest_same_log.py`: runs chinook's own `ingest.sql` on both files and compares every block's output;
- `q1_gold.sql` and `q2_chinook.sql`, run by `rq.py`: the Spider question on both files;
- `profile.py` and `coltypes.py`: per-column profile and results types;
- `gold_check.py`.

The raw outputs are `out_*.txt` next to each script. A reference such as `[c1]` names a script; `[q1:thresholds]` names a block.

## 0. What this catalog is

- **Dataset.** This is **Chinook** by Luis Rocha (`lerocha/chinook-database`), in the **upstream SQLite packaging**. The evidence:
  - The tables have upstream's singular PascalCase names: `Album`, `Artist`, `Customer`, `Employee`, `Genre`, `Invoice`, `InvoiceLine`, `MediaType`, `Playlist`, `PlaylistTrack`, `Track`.
  - The DDL is upstream's: bracket-quoted, `CONSTRAINT [PK_Album] PRIMARY KEY ([AlbumId])`, `ON DELETE NO ACTION`.
  - There is **no AUTOINCREMENT**, so there is no `sqlite_sequence`, and there is no `sqlite_stat1`. The file has 21 indexes against chinook.sqlite's 10 [c2].
  - `chinook.sqlite` is the sqlitetutorial.net repackaging of the same data, with plural snake_case names (`albums`, `invoice_items`, `media_types`, `playlist_track`).
- **Row counts** [profile, c1]: Artist 275, Album 347, Genre 25, MediaType 5, Track 3,503, Playlist 18, PlaylistTrack 8,715, Employee 8, Customer 59, Invoice 412, InvoiceLine 2,240. Total 15,607, the same as chinook.
- **Era.** Invoice dates are 2009-01-01 .. 2013-12-22 [q1:date_range], the pre-1.4.5 era, the same as chinook.sqlite.
- **Licence.** MIT ("Copyright (c) 2008-2024 Luis Rocha"), as for chinook.
- **Nature.** The catalog is real iTunes metadata; the sales are generated by a deterministic rule (see `chinook.md` §4).

- **0 differing rows** in total, under both the contract comparison and a strict comparison of storage class and value [c1: `TOTAL differing rows: contract 0, strict 0`].
- **Same physical order.** Even the physical row order and the rowids are identical, table by table [c2]. That includes PlaylistTrack's non-PK order: only 162 of 8,715 rows sit at their PK rank, in both files [q1:rowid_order_vs_pk, q2:rowid_order_vs_pk].

So the keys, FKs, orphans, coverage and quirks are exactly those measured in `chinook.md` §1 and §4. I do not repeat them here.

## 2. Event catalogue

**Reuse chinook's events unchanged.** chinook's own `ingest.sql` was run on chinook.sqlite, and again on music.sqlite with only the 11 `FROM`/`JOIN` table names renamed. All 11 blocks gave **identical output: ordered, typed, 15,607 of 15,607 rows** [c3]. These are the 9 entity blocks and the 2 event blocks, `invoice_issued` (412) and `invoice_line_added` (2,240).

Because ingest is deterministic, the music log is the chinook log: the same 2,652 events, the same 12,955 entity rows, the same seq. The event times are natural (InvoiceDate) for both events, and set by rule for customers' `created_at` (the first invoice), exactly as in `chinook.md` §2. Nothing new is an entity or an event.

## 3. Rebuild rules and blockers to an exact round trip

`chinook.md` §3 applies verbatim. In particular, Total = (Σ line cents) / 100.0 (412 of 412), and prices are cents / 100.0. The only music-specific change is the output table names. chinook's `build.sql` bodies read the entity and event views (`genres`, `invoices`, …), which are pack names, not source names. So a music build.sql is chinook's with each `-- table: <name>` header renamed, and the SELECTs untouched:

```text
-- table: Genre          (was genres)        -- table: Playlist       (was playlists)
-- table: MediaType      (was media_types)   -- table: PlaylistTrack  (was playlist_track)
-- table: Artist         (was artists)       -- table: Employee       (was employees)
-- table: Album          (was albums)        -- table: Customer       (was customers)
-- table: Track          (was tracks)        -- table: Invoice        (was invoices)
-- table: InvoiceLine    (was invoice_items)
```

Because the source tables are identical, chinook's proven round trip transfers row for row. There is no `sqlite_sequence` to recreate, since music's DDL has no AUTOINCREMENT [c2].

**Verdict:** exact, yes, by construction. I have not run `dataset build` / `verify` for a music project, because that would mean writing outside the research folder.

## 4. Measured quirks

None beyond chinook's (`chinook.md` §4: the 7-invoice cycle, Fibonacci-like date gaps, deterministic customer and track walks). The packaging differences are listed in §1.

## 5. Distributions to fit (stage 2)

Identical to `chinook.md` §5. local244 adds one fact: track durations are very skewed. The mean is 393,599 ms against a max of 5,286,953 [q1:thresholds]. So "short" means < 3.29 min and "long" means > 47.3 min, and most revenue (1,817.55 of 2,328.60) is "medium" [q1:local244].

## 6. simkit mapping sketch

There are two ways to get there. **I recommend option A.**

**A. `music` as a thin dataset over chinook's pack** (preferred):
- `datasets/music/specs/pack.py`: chinook's pack, imported or copied (the same entities and events, `SCHEMA_VERSION`).
- `source.toml`: `file = "music.sqlite"`, with the 11 PascalCase table keys (`Album = ["AlbumId"]`, `PlaylistTrack = ["PlaylistId", "TrackId"]`, …).
- `ingest.sql`: chinook's with the 11 FROM/JOIN renames. Its output is proven identical [c3].
- `build.sql`: chinook's with the 11 `-- table:` renames above.
- `queries/local244.sql`: over the PascalCase names.

The log equals chinook's, so a builder may store it once and let `music` reference it. That choice is left to whoever owns the data-root layout.

**B. Fold local244 into `chinook`.** Add `datasets/chinook/specs/queries/local244.sql` written over chinook's names. Its answer on chinook.sqlite equals the gold `_a` [q2:local244_chinook]. This is the cheapest option, but `results/` would then never hold music's own table names, and the contract says a Spider2 dataset's results hold every *source* table. So B covers the question but not the `music` catalog itself.

Either way, stage 2 is chinook's (customer owners, a catalog source); nothing changes.

## 7. Open questions and risks

- **One log, two datasets.** Under A, the data root holds two copies of the same 2,652-event log unless the layout allows a reference. Duplication is cheap at this size (well under 1 MB); deduplication is a layout decision.
- **Upstream version.** The data matches chinook.sqlite exactly, so the open question in `chinook.md` §7 (exactly which 1.4.x build) carries over unchanged.
- **local244's float sums.** The two gold CSVs disagree in the last digits of the revenue sums. Compare source with rebuilt, with the 1e-9 tolerance, not with gold.
- **Not run end-to-end.** The equivalence is proven at the source level (0 differing rows) and at the ingest level (identical ordered output). A real `dataset build`/`verify` of `music` is the builder's first step.

**Summary**
- Exact round trip: yes. music.sqlite equals chinook.sqlite in all 11 tables, with 0 differing rows (strict and contract) and the same row order; chinook's ingest yields identical output on both (15,607 rows).
- Dataset name: `music`, a thin dataset reusing chinook's pack, events and build with renamed tables. The fallback is to fold local244 into `chinook`.
- Event types 2 (`invoice_issued`, `invoice_line_added`); entities 9. Both counts are chinook's, unchanged.
- Event shape: as chinook, partly imposed. The invoice events are natural, but it is a small log over large static catalog entities, and customers' creation time is a rule.
- Hardest blocker: none for exactness. The only decision is whether to store a second copy of chinook's log under `music` or reference it.
