# stacking (Spider 2.0-lite): reverse-engineering an ML model-stacking experiment log into an event log

Source: `data/spider2/stacking.sqlite`, opened read-only (`sqlite3 -readonly`, `python3 -I` with `mode=ro`).
Scripts: [`scripts/stacking/`](scripts/stacking/) (`00_fetch_gold.sh`, `01_inventory.sql`, `02_values.sql`, `03_derived.sql`, `04_gold.sql`, `05_dists.py`, gold CSVs in `gold/`). Each script's raw output is the `out_<script>.txt` next to it.

## 0. What this catalog is

### Origin

The file is the **results store of one person's automated model-stacking tool**, run over 20 Kaggle datasets. Each `problem` row holds a Kaggle URL (iris, concrete, Delaney solubility, … PSS3E5 = Playground Series S3E5) and its target column. For each problem, the tool:
- **profiles features** (`eda`);
- **trains a pool of level-0 models** with short codes: RFCG/RFCE, DTCG/DTCE, LOGRLCV, HGBC, KNCD, … and their R twins for regression;
- **stacks them under a level-1 model** ("regression" or "tree");
- **repeats this over 3 steps.** It keeps the top `nb_model` models after step 1, and the top `nb_feature` features at step 3 (§2).

The tool is versioned per problem, with 3–8 versions each.

Evidence that it is real tool output:
- The three SQLite views (`stack_ok`, `solution_ext`, `stack_ok_score`) are the tool's own reports.
- Importances sum to 1 per step: 303/303 for model importance, and 303/303 within 1e-14 for feature importance (`02_values.sql`).
- Scores have the 15–17 significant digits of numpy floats.

The data is **real experiment output, not generated by hand**. The author is unidentified. Licence: unstated. The underlying Kaggle datasets carry their own licences, but none of their data is in this file.

## 2. Event catalogue

One run's lifecycle, measured in `03_derived.sql`:
1. **Configure.** A `solution` row is written.
2. **Profile features.** An `eda` row per feature: drop_user (205), drop_correlation (151), target (exactly 1 per run). `type` and `range` are NULL exactly on the 306 user-dropped and target rows.
3. **Step 1.** Every candidate model is scored (6–19 per run). Feature importance covers every eda feature with drop_user = 0 and target = 0, **including the correlation-dropped ones** (0 missing, 0 extra).
4. **Step 2.** The pool is cut to `nb_model` models: the count equals nb_model in 99 of 101 runs. The selection rule is not reproducible from step-1 test score or step-1 model importance: they agree on only 1,291 and 1,414 of 1,661. Step-2 scores equal step 1's for 443 of 454 models. The feature set is the same as step 1's, but 1,020 of its importance values differ.
5. **Step 3.** The same models as step 2 (0 differences), and features cut to the **top `nb_feature` by step-2 importance** (0 exceptions). The count is below nb_feature in 36 runs that have fewer features. Scores are recomputed: 281 of 454 change.

|---|---|---|---|---|---:|
| `problems` entity | name | **rule:** the first run's time | path `text`, type `cat`, target `text` (verbatim, one has a trailing space) | problem | 20 |
| `solutions` entity → `run_configured` | (name, version) | **rule:** run clock | problem `ref`, version `i32`, correlation `f64`, nb_model `i32`, nb_feature `i32`, score `f64`, test_size `f64`, resampling `i32` | solution | 101 |
| `feature_profiled` | run | rule (= run time) | feature `text`, type `opt(cat)`, range `opt(text)`, drop_user, drop_correlation, target `i32` | eda | 1,547 |

| `feature_weighted` | run | rule | step, feature, importance `f64` | feature_importance | 2,887 |
| `step_completed` | run | rule | step `i32`, L1_model `cat`(regression, tree) | model | 303 |

**5 event types, 2 entities, 10,297 log rows:** 10,176 business events and 121 entity creations.

- **The run clock (rule).** Run k, the k-th solution rowid, starts at T0 + k hours. Its eda events are at +0. Its step-s events are at + s minutes, ordered score → model weights → feature weights → step_completed, with `ord` = source rowid.
- **Only the order is natural.** It is the source's real insertion chronology (§1). The spacing is not.
- **Not entities:**
  - **Models:** 46 codes. They are `text` labels with no table of their own, and their meaning (RF/DT/LOGR/KNN/GP/MLP/…, plus gini/entropy suffixes) is inferred from the names only.
  - **Features:** names local to a dataset, with no table.
  - **Steps:** the `model` rows are events (`step_completed`), because they mark the end of a step and carry its L1_model.
- **The views** produce no events.

## 3. Rebuild rules and blockers to an exact round trip

Views (DuckDB over the log):
- **problem** from `problems`.
- **solution** from `solutions`.
- **eda, model_score, model_importance, feature_importance, model:** one view per event type. Each projects the payload back with name and version from the run's `solutions` entity.

Blockers and rules:
1. **NUMERIC columns hold integers and reals.** test_score is 142 integer and 2,730 real. train_score is 795 integer, and importances 217 and 513 integer, the integers being exactly 0 or 1 (`02_values.sql`).
   - By the contract, a NUMERIC column is float64 and 1 vs 1.0 compares by value, so the column is **not mixed**.
   - The rebuilt file will store `1.0` (REAL), and `typeof()` would differ. No question uses typeof.
2. **Floats must round-trip bit-exact.** Strong vs soft is decided by `max(test_score) < / = Stack.test_score`, which gives 47 soft ties (14 + 13 + 20). f64 JSON in its shortest round-trip form preserves every double. **Any decimal rounding in the pipeline would flip ties.** Scores range down to −65,597,190.86 (54 negative test scores, i.e. negative R²).
3. **`eda.range` is declared BLOB but holds text:** 1,241 text and 306 NULL, e.g. `[4.3, 7.9]` and `['tube', 'annulus', 'plate']`. Keep it as byte-exact text. The results column type is string.
4. **The views must be replayed, or the saved queries inlined.** local262 and local263 read naturally from `stack_ok`. The view DDL, with its `ORDER BY` inside the `UNION ALL` and a bare `C.L1_model` in a `GROUP BY` that is safe because L1_model is constant per run, should be carried as dataset DDL, or the saved queries rewritten over base tables. `04_gold.sql` shows that both give the same answers.
5. **CHECK constraints use double-quoted strings** (`type IN ("classification", "regression")`). SQLite reads those as string literals; DuckDB DDL would not. This matters only if the DDL is replayed outside SQLite.
6. **Text quirks:**
   - `problem.target` for concrete ends in a space (48 characters).
   - In 4 runs the eda target feature differs from `problem.target`: concrete uses `Strength`/`csMPa`, and iris uses `Species` vs `variety`. Different Kaggle file versions, measured, kept verbatim.
7. **All times are rules.** Even T0 is arbitrary. The latest problem, PSS3E5, is a Kaggle Playground episode from early 2023. That is a plausible anchor for T0, but it comes from outside the data.

Verdict: **exact round trip feasible**. 7 tables come from 121 entity rows and 10,176 events, and the 3 views from their stored SQL.

## 4. Measured quirks

- **Score ties are common.** At steps 1/2/3 the Stack score is strong (beats the best base model) in 27/32/33 runs, soft (ties it) in 14/13/20, and weaker in 60/56/48 (`03_derived.sql`). Stacking more often loses than wins.
- **Integer 0/1 scores:** 120 test scores are exactly 1 (perfect accuracy) and 22 are exactly 0. 777 train scores are exactly 1.
- **Huge negative R²:** 54 test scores and 50 train scores are below 0, the minimum being −6.6e7. Any "average score" query is dominated by them.
- **The importance mismatch** on Liver disease #5 step 2 (§1): 1 orphan importance and 3 scored models without importance.
- **Selection mismatches:** Critical Heat Flux #5 keeps 5 models with nb_model 6, and PSS3E5 #4 keeps 1 with nb_model 5.
- **Config constants:** `correlation` = 0.75 in all 101 runs, test_size 0.33 in 90 runs, score 0.7 in 69 runs (`02_values.sql`).
- **Typos are data:** `kindey stone urine analysis`.

## 5. Distributions to fit (stage 2)

From `05_dists.py` and `02_values.sql`:
- **Runs:** versions per problem: 3 → 4 problems, 4 → 2, 5 → 8, 6 → 2, 7 → 3, 8 → 1. 14 problems are classification and 6 regression. Runs arrive per problem in bursts, with 5 later revisits (§1).
- **Config changes between consecutive versions** (81 transitions): nb_model changes 63 times, nb_feature 20, score 20, resampling 3, test_size 2. The tool's user mostly tunes the pool size.
- **eda features per run:** median 11, p90 50, range 2–51.
- **Models per run:**
  - step 1: median 18, range 6–19;
  - steps 2 and 3: nb_model, median 5, range 1–7. nb_model values: 5 → 50, 3 → 27, 7 → 12, others ≤ 5.
- **Stack test score:**
  - classification step 1: median 0.861, p10 0.741;
  - regression step 1: median 0.910;
  - feature cut to step 3: regression median 0.880, min 0.396. Fewer features cost accuracy.
- **Train − test gap (base models):** classification median 0.036, p90 0.22; regression median 0.086.
- **Version to version (Stack step 3):** up 36, down 35, same 10. There is no learning trend.
- **Conversion through the lifecycle:** strong at any step in 43 of 101 runs (37 + 6), soft only in 21, neither in 37 (`04_gold.sql` R3).

## 6. simkit mapping sketch

```python
p.entity("problems", key="problem_key", cols={"ext_id": text(doc="name"), "path": text(),
         "type": cat("classification", "regression"), "target": text(doc="verbatim; concrete's has a trailing space")})
p.entity("solutions", key="run_key", doc="One run (problem, version); created_at = run clock (rule)",
         cols={"ext_id": text(doc="name || '#' || version"), "problem": ref("problems"), "version": i32(),
               "correlation": f64(), "nb_model": i32(), "nb_feature": i32(), "score": f64(),
               "test_size": f64(), "resampling": i32()})
row = {"run": ref("solutions"), "src_rowid": i64()}
p.event("feature_profiled", cols={**row, "feature": text(), "type": opt(cat("num", "cat")), "range": opt(text()),
        "drop_user": i32(), "drop_correlation": i32(), "target": i32()})
p.event("model_scored", cols={**row, "step": i32(), "model": text(), "train_score": f64(), "test_score": f64()})
p.event("model_weighted", cols={**row, "step": i32(), "model": text(), "importance": f64()})
p.event("feature_weighted", cols={**row, "step": i32(), "feature": text(), "importance": f64()})
p.event("step_completed", cols={**row, "step": i32(), "L1_model": cat("regression", "tree")})
```

- **Ingest:**
  - every event block has `owner=run ord=src_rowid`;
  - times: `datetime(T0, '+' || run_rowid || ' hours', '+' || step || ' minutes')`;
  - blocks in the order eda → scores → model weights → feature weights → step_completed, so that equal times keep the lifecycle order;
  - entities `ORDER BY rowid`.
- **build.sql:** one block per table, as in §3. Replay the 3 view DDLs after the tables, or inline them in the saved queries.
- **Saved queries:**
  - local262 (7 names);
  - local263 (strong 37, soft 17, with one status per run);
  - local264 (regression 213).
  - All are exact on integers. local262 and local263 hinge on float ties.
- **Stage 2:** a run is a state machine per problem: configure → profile → step 1 (pool) → select nb_model → step 2 → cut features to nb_feature → step 3. Scores come from a per-problem difficulty and per-model-family offsets.
  - Laws that hold: 3 steps per run; one Stack per step; importances sum to 1; step-3 features ⊆ top-nb_feature of step 2; step-3 models = step-2 models.
  - Laws that do **not** hold: "step-2 model count = nb_model" (2 exceptions) and "model_importance covers exactly the scored models" (1 run).

## 7. Open questions and risks

- **Every time is a rule.** Is a 1-hour run clock acceptable, or should the dataset carry no time beyond the order (all events at T0, order by `ord`)? The insertion order is real; spacing is not.
- **Views as part of the dataset.** The contract rebuilds tables. Should `dataset.toml` carry view DDL so that `verify` can run questions written against `stack_ok`, or must every saved query be view-free?
- **local263's accepted reading** (one status per run, strong wins) is an interpretation. The question text can also be read per step (78 / 36). Only `_a` exists, and it matches the per-run reading.
- **The step-2 model selection rule** is not recovered: neither top-test-score nor top-importance matches. Stage 2 would need it to generate realistic pools; stage 1 does not.
- **Float exactness through every engine.** Any engine or JSON path that prints fewer than 17 significant digits breaks the soft-tie counts.

## Summary

1. **Feasible:** yes. All 7 tables rebuild exactly from 2 entities and 5 event types. The 3 SQLite views are pure SQL over `model` and `model_score`, and need their DDL replayed or inlined.
2. **Dataset name:** `stacking`. Saved queries: local262, local263 (per-run status), local264.
3. **Events and entities:** 5 event types (`feature_profiled` 1,547, `model_scored` 2,872, `model_weighted` 2,567, `feature_weighted` 2,887, `step_completed` 303), 2 entities (`problems` 20, `solutions` 101).
4. **How event-shaped:** mostly imposed. It is a real experiment log with a true insertion order (run → step), but there is not one timestamp, so every time is a rule.
5. **Hardest blocker:** exact float equality. Strong vs soft, and so all 3 answers, turns on `max(test_score) = Stack score` ties (47 of them), so every score must survive the log bit-exact. Next is the views, which the table-only rebuild does not recreate.
