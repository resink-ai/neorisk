# ecommerce

## What this is

A mid-size online store with a referral program: shoppers sign up, browse in sessions, place orders of one or two SKUs, sometimes return them and sometimes move region; a referred shopper's first order of at least $30 pays the inviter a $10 bonus from a monthly budget. The same event log is modeled three ways — a star schema, a Data Vault and an anchor model — so one dataset tests a processor on three shapes of output.

Version `v1`, kind `synthetic`, from `examples/ecommerce` (profile `sample`, seed 7). The input is one ordered event log of 15,090 events; the output is 63 tables in three designs (`star`, `dv`, `an`), and the answers to 3 questions.

## Raw data

Generated by the `datagen` pack [`examples/ecommerce/specs/pack.py`](../../examples/ecommerce/specs/pack.py); the business is described in its brief, [`examples/ecommerce/specs/brief.md`](../../examples/ecommerce/specs/brief.md). Licence: generated, no third-party data. Money is integer cents; times are UTC.

## How the log was made

`uv run dataset build ecommerce` runs the pack with the `sample` profile (600 users over 20 days), seed 7, and no overlay, then writes the run as one log. Each entity row becomes an `<entity>_created` event at its creation time (no domain names); business events keep their columns. Every business event is keyed on the column a Kafka consumer would partition on (`[recipe.owners]` in `dataset.toml`): `user_id` for every shopper event and for both referral-bonus events (the inviter), `sku_id` for `stock_restocked`. The `reservation_*` events of the `std.reservations` recipe keep the default owner, their partition.

The designs read the log alone. Simkit's own tables are used only to grade them (the `[[check]]` entries) and to answer the questions (`oracle.sql`).

Two quirks of the pack show in the log and the designs handle them on purpose:

- A user's first session can run at the instant of signup, so 6 `address_changed` events share `event_time` with their user's creation, and 2 change the region to the one it already was.
- The pack picks an inviter from the users already *inserted*, not already *created*, so an inviter can be created after the invitee; 2 of the 20 bonuses are paid to an inviter whose account starts later.

## Designs

All three designs cover the same scope: users (with their region history from `address_changed`), devices, SKUs, orders and order lines, sessions and product views, returns, and referral bonuses (paid and rejected). Left out of every design: the `reservation_*` events of the `std.reservations` recipe (internal inventory bookkeeping), `stock_restocked`, `checkout_failed` and `verification_failed` (the last two have no rows in this run), and `user_signed_up`, whose payload repeats the user's creation row at the same instant. The designs follow the patterns of the *Beyond Facts & Dimensions* atlas.

**`star` — star schema (Kimball).** Grain: one row per order (`star_fact_orders`), order line, session, product view, return and referral-bonus decision; dimensions for users, devices and SKUs. `star_dim_users` is SCD2 on `region`: one version per creation and per `address_changed`, with `users_sk` (row number over `user_id`, then `valid_from`, then log order), `valid_from`, `valid_to` (null = open) and `is_current`; the static attributes repeat on every version. A version that is replaced at its own instant (signup and an address change at once) is kept with `valid_to = valid_from` and binds no fact. Every fact carries the `users_sk` in force at its event time (`valid_from <= t < valid_to`); a bonus paid before its inviter's account exists points at the inviter's first version. The atlas's verdict holds here: one join answers "as of then" questions, at the cost of a surrogate key that every fact must look up and of repeating the static attributes on each version. No `star_dim_date` (a date dimension cannot be checked against a simkit table) and no accumulating order snapshot (an order's only later stage is a return, kept as its own fact).

**`dv` — Data Vault 2.0.** Hubs for users, devices, SKUs, orders and sessions (`<e>_hk = md5(key as text)`); links for device ownership, invitation, order (order, user, device), order line (order, SKU, `line_id` as dependent child key), session (session, user, device), product view (session, SKU, `view_id`) and referral bonus (inviter, invitee). Satellites hold the attributes, split by rate of change: `dv_sat_users_profile` (age band, acquisition: static) and `dv_sat_users_region` (one row per change). Every satellite row has `hashdiff` = md5 of its attributes joined by `'||'` (nulls as `''`) and is written only when the hashdiff differs from the parent's previous row, so the 2 address changes to the same region add no row; when two values share one instant, the later in log order is the value at that time (the satellite key is parent + `load_dts`). `load_dts` is the event time, `record_source` the log event type. As the atlas says, the vault is insert-only and auditable and absorbs new sources without remodeling, but every question becomes a chain of hub–link–satellite joins and a point-in-time lookup.

**`an` — anchor modeling.** An anchor per entity and per business event (users, devices, SKUs, orders, order lines, sessions, product views, referral bonuses), each with its identity and time; one table per attribute; one tie per relation, named `an_<e1>_<role>_<e2>` (e.g. `an_orders_placedby_users`, `an_order_lines_for_skus`). Static attributes have no time column; historized ones have `changed_at` and one row per change: `an_users_region` (same rules as the vault's satellite: same-instant values collapse to the last, restatements are dropped) and `an_orders_return_amount`. Nothing is null: a user without an inviter has no tie row, a rejected bonus no amount row. The atlas's trade-off shows: adding an attribute is adding a table and history is native, but the model is the widest (34 tables) and every question joins one table per attribute it touches.

## Questions

- **`q1_revenue_by_region_at_order`** — orders and order amount by the user's region in force at order time. Needs history: 26 users move, and the answer differs from grouping by either the signup region or the current one. Star reads the version through `users_sk`; vault and anchor look up the latest region row at or before the order time.
- **`q2_units_by_category`** — order lines, units and line amount by SKU category. A plain fact-to-dimension rollup; it checks that every design keeps order lines (not just the first line on the order) and joins them to SKUs.
- **`q3_bonus_by_channel`** — referral bonuses paid (count, amount) by the inviter's acquisition channel. Joins the bonus to the inviter, not the invitee; acquisition is static, and 2 bonuses are paid before their inviter's account is created, which a naive "version in force" join in the star would drop.

## Extend

- **More rows:** run the pack with a bigger profile or `--set` (e.g. `uv run datagen run examples/ecommerce --profile sample --set users=5000`) and make it a new dataset or version with that recipe in `dataset.toml`; every design and question is written against the log and keeps working.
- **An overlay:** `bounty_hunters` (referral rings) as a new dataset, e.g. `datasets/ecommerce-bounty_hunters/` with `overlay = ["bounty_hunters"]`; it adds labels and new actors, so owners and checks may need entries.
- **A new design:** add its id to `designs` (three per dataset), write `specs/<design>.sql` with `<design>_`-prefixed `-- table:` blocks over the log views, add `[[check]]`s, and an answer file in every question folder.
- **A new question:** a folder under `specs/questions/<id>/` with `oracle.sql` (reads `sim.<table>` only) and one `<design>.sql` per design (reads that design's tables only); all answers must have the same columns and agree with the oracle.
- **A new engine port:** write `engines/<engine>/` from `specs/<design>.sql`. It must read only the log and match `results/` exactly.

Any change to `specs/`, `dataset.toml` or the pack changes the build. Once a version is recorded in `v1.lock.json`, changed output needs a new version (`v2`).
