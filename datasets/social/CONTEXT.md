# social

## What this is

A small social network: users follow each other, post, and see, like and repost what the accounts they follow put in front of them. The follow graph is built once at the start (popular accounts attract most follows, and a quarter of follows are returned); each post starts a cascade: the author's followers see it a few hours later, some like it, some repost it, and a repost exposes the reposter's followers in turn. A user sees a cascade at most once and reposts it at most once. The same event log is modeled three ways — a star schema with an accumulating snapshot of each cascade, a Data Vault and an activity schema — so one dataset tests a processor on three shapes of output: the follow graph is links, engagement is a stream.

Version `v1`, kind `synthetic`, from `examples/social` (profile `sample`, seed 7). The input is one ordered event log of 25,892 events; the output is 18 tables in three designs (`star`, `dv`, `act`), and the answers to 3 questions.

## Raw data

Generated by the `datagen` pack [`examples/social/specs/pack.py`](../../examples/social/specs/pack.py); the business is described in its brief, [`examples/social/specs/brief.md`](../../examples/social/specs/brief.md). Licence: generated, no third-party data. There are no amounts; times are UTC.

## How the log was made

`uv run dataset build social` runs the pack with the `sample` profile (500 users over 5 days), seed 7, and no overlay, then writes the run as one log. Each entity row (`users`, `follows`) becomes an `<entity>_created` event at its creation time (no domain names); business events keep their columns. Owners (`[recipe.owners]` in `dataset.toml`): every post event (`post_created`, `post_viewed`, `post_liked`, `post_reposted`) is keyed on `post_id`, the cascade's root post, because the pack's cascade owner (one per root post) emits all of them, and a consumer rebuilding a cascade — its reach, its depth, the one-view-per-user rule — needs the post and every view, like and repost of it in one ordered partition (keying on the acting `user_id` would scatter a cascade across its viewers; keying on a repost's own `repost_id` would split the cascade at every repost). The pack has no `std` recipes, so there are no internal events.

The designs read the log alone. Simkit's own tables are used only to grade them (the `[[check]]` entries) and to answer the questions (`oracle.sql`).

Facts of this run the designs handle on purpose:

- `post_id`, `repost_id`, `via_post` and `parent_id` are plain integers in the pack, not references, and there is no posts entity: a post exists only through its `post_created`, a repost only through its `post_reposted`. Originals and reposts draw their ids from one sequence, so the 306 root posts and 462 reposts have 768 distinct ids.
- `post_id` on every view, like and repost is the cascade's **root** post, never a repost: engagement is credited to the root post's author, whoever's repost exposed the viewer. `via_post` (on a view) and `parent_id` (on a repost) are the root or a repost of the same cascade; 4,819 of the 8,076 views came through a repost.
- Every user and every follow is created at the run's start (one instant), so the follow graph never changes and no entity attribute changes in the log. Each follow pair occurs once.
- Every user has between 10 and 169 followers in this run, so the 0 and 1–9 buckets of `q3_follower_buckets` are empty (the answer still lists them, at 0). 24 of the 500 users are `popular`; 12 of them have 100 or more followers.
- A like happens only at the view and a repost only after it: a user likes and reposts a cascade at most once. Depth 1 is a repost of the root itself (179 of them); the deepest cascade reaches depth 8. No cascade reaches the pack's cap of 400 views (the largest has 266).

## Designs

All three designs cover the same scope: users, the follow graph, root posts, and each cascade's views, likes and reposts (with the repost's root, parent and depth). Nothing is left out: every event of the log is in every design. No entity attribute changes in the log and the graph is built once, so no design keeps attribute history: the history here is the cascade, a tree of reposts under one root post that grows over the run. Every design credits a view, like or repost to the root post's author, and a cascade's depth is the largest `depth` of its reposts (0 if nobody reposted it). The designs follow the patterns of the *Beyond Facts & Dimensions* atlas.

**`star` — star schema (Kimball).** A static `star_dim_users` (tier, creation time) keyed on `user_id` (no SCD2: nothing changes, so a surrogate key would add a lookup and buy nothing). It plays two roles in the engagement facts: the acting user (`user_id`) and the root post's author (`author_id`, looked up from the post fact at build time). Posts are not a dimension: simkit has no posts table to check one against, and a post's only attributes, its author and time, are the post fact. `star_fact_follows` is a factless fact, one row per follow edge (follower, followee, time). One transaction fact per business event, at the grain of the event: post (`star_fact_posts`), view (with `via_post`), like, and repost (`repost_id`, root `post_id`, parent post and parent user, depth). `star_fact_cascade_lifecycle` is the accumulating snapshot: one row per root post with its author, its views, likes, reposts and `max_depth`, and its milestones (posted, first view, first like, first repost, last activity). The atlas's verdict holds: the snapshot answers "how far did each post travel" with one scan, at the cost of a row rewritten at every view in a live system. Lifecycle facts are exempt from `[[check]]`; every other star table is checked against simkit. No calendar dimension (a date dimension cannot be checked against a simkit table).

**`dv` — Data Vault 2.0.** Hubs for users and posts (`<e>_hk = md5(key as text)`). A post's business key is its id from the pack's one post id sequence: `post_id` for an original, first seen at `post_created`, and `repost_id` for a repost, first seen at `post_reposted` (the hub row's `record_source` says which), so a repost is a post that can be a later repost's parent and the post a view came through. Links: `dv_link_follow` (follower, followee, with `follow_id` as dependent child key, since in a live network a pair can be followed, dropped and followed again); `dv_link_post_author` (post, user), for originals and reposts alike; `dv_link_view` (root post, viewer, the post it came through) and `dv_link_like` (root post, user), each with the log's event id as dependent child key (`view_id`, `like_id`), because nothing outside this pack's laws stops a user seeing or liking a post twice; and `dv_link_repost` (the repost's own post, its cascade's root, its parent). Satellites: the user's `profile` (tier) and the repost's `details` (depth), each with `hashdiff` = md5 of its attributes joined by `'||'` (nulls as `''`), written only when the hashdiff changes. `load_dts` is the event time, `record_source` the log event type. As the atlas says, the follow graph and the repost tree are links, so adding a new relationship (a reply, a mention) is a new link and nothing is remodeled; the price is hops: a cascade's engagement by author tier walks root post → authorship link → user hub → profile satellite, and who reposted from whom takes the repost link and two authorship links.

**`act` — activity schema.** One stream, `act_user_stream`, with one row per thing a user does, in the standard columns (`activity_id, ts, customer, activity, feature_1, feature_2, feature_3, revenue_impact, link, activity_occurrence, activity_repeated_at`), and the customer table `act_user` (tier, creation time). `customer` is the acting user, `ts` the event time. The activities and their text features:

| Activity | Source | `activity_id` | `feature_1` | `feature_2` | `feature_3` | `link` |
|---|---|---|---|---|---|---|
| `followed_user` | `follows` | follow_id | followee_id | — | — | — |
| `created_post` | `post_created` | event_id | — | — | — | post_id |
| `viewed_post` | `post_viewed` | event_id | author_id | via_post | — | root post_id |
| `liked_post` | `post_liked` | event_id | author_id | — | — | root post_id |
| `reposted_post` | `post_reposted` | event_id | author_id | repost_id | depth | root post_id |

`link` is the cascade's root post id as text, the post page every post activity is about. `author_id` is the user who created the root post: it is the `customer` of the `created_post` with the same `link`, copied onto every engagement row at build time so that engagement *received* is one filter on `feature_1` rather than a self-join of the stream; a user's followers are likewise the `followed_user` rows with that user in `feature_1`. A follow takes its `follow_id` as `activity_id` (a follows row has no event id in the views), so the stream's key is (`activity_id`, `activity`), not `activity_id` alone. A repost's parent post and parent user are not kept (three features are all there is; the depth is). `revenue_impact` is null throughout: nothing here moves money. `activity_occurrence` is the 1-based count of the customer's activities of that kind in `ts` order (ties by `activity_id`; every follow shares the run's first instant), and `activity_repeated_at` the `ts` of the customer's next one, else null. Each activity's keys are checked against its simkit table. As the atlas says, one narrow table holds every user's journey and engagement funnels (viewed, then liked or reposted) fall out of it; the price is that the graph, which is a relation between two customers, is flattened into one side's activity, typed ids become text features to cast back, and anything about the post rather than the actor (its author) must be denormalized onto the row or rejoined through the stream.

## Questions

- **`q1_engagement_by_tier`** — per author tier: the root posts its users created, and the views, likes and reposts those posts' cascades received. It needs the cascade bound to its root's author: every engagement event names the root, never the repost that exposed the viewer, so the star reads `author_id` off its facts, the vault walks root post → authorship link → user → profile satellite, and the stream reads the author from `feature_1`. Both tiers are in the answer.
- **`q2_cascade_depth`** — root posts by the maximum repost depth of their cascade (0 when nobody reposted it). Needs the cascade's structure: the star reads `max_depth` from its lifecycle snapshot, the vault takes each repost link's root and its depth satellite, the stream groups `reposted_post` rows by `link` (the root) and takes the largest `feature_3`. Every root post counts, including the 173 never reposted.
- **`q3_follower_buckets`** — users by follower-count bucket (0, 1–9, 10–99, 100+) and tier, every bucket and tier listed (8 rows, empty ones at 0). A user's followers are the follows with that user as followee: the star counts its factless follow fact, the vault the follow links on the followee's hub key, the stream the `followed_user` rows with that user in `feature_1` — so the followee, not the customer, is the user counted.

## Extend

- **More rows:** run the pack with a bigger profile or `--set` (e.g. `uv run datagen run examples/social --profile sample --set users=1500`) and make it a new dataset or version with that recipe in `dataset.toml`; a bigger run may hit the cascade cap of 400 views, which every design already handles (it only stops views). Every design and question is written against the log and keeps working.
- **An overlay:** the pack has none yet; an overlay (say, a bot ring that follows and reposts in bursts, with labels) would be a new dataset, e.g. `datasets/social-<overlay>/` with `overlay = ["<overlay>"]`; it adds labels and new actors, so owners and checks may need entries. If it creates follows or changes tiers during the run, `star_dim_users` needs SCD2, the vault a new profile satellite row per change, and the stream a new activity.
- **A new design:** add its id to `designs` (three per dataset), write `specs/<design>.sql` with `<design>_`-prefixed `-- table:` blocks over the log views, add `[[check]]`s, and an answer file in every question folder.
- **A new question:** a folder under `specs/questions/<id>/` with `oracle.sql` (reads `sim.<table>` only) and one `<design>.sql` per design (reads that design's tables only); all answers must have the same columns and agree with the oracle.
- **A new engine port:** write `engines/<engine>/` from `specs/<design>.sql`. It must read only the log and match `results/` exactly.

Any change to `specs/`, `dataset.toml` or the pack changes the build. Once a version is recorded in `v1.lock.json`, changed output needs a new version (`v2`).
