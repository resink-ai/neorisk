# layer1

## What this is

The transaction envelope of a layer-1 chain: wallets send transfers and contract calls to one chain shard, which holds every balance and nonce and builds a block every 12 seconds. At each block the chain processes its queue in arrival order: a transaction whose nonce is not the sender's next, or whose sender cannot cover the maximum fee plus the value, is dropped; an included one bumps the nonce and pays gas, and a call that reverts still pays gas but moves nothing. The same event log is modeled three ways — a star schema with an accumulating snapshot of the transaction lifecycle, an activity schema and one big table per grain — so one dataset tests a processor on three shapes of output.

Version `v1`, kind `synthetic`, from `examples/layer1` (profile `sample`, seed 7). The input is one ordered event log of 11,003 events; the output is 13 tables in three designs (`star`, `act`, `obt`), and the answers to 3 questions.

## Raw data

Generated by the `datagen` pack [`examples/layer1/specs/pack.py`](../../examples/layer1/specs/pack.py); the business is described in its brief, [`examples/layer1/specs/brief.md`](../../examples/layer1/specs/brief.md). Licence: generated, no third-party data. Amounts (genesis, value, fee) are integer gwei, gas is integer gas units (fee = gas used × 20 gwei); times are UTC.

## How the log was made

`uv run dataset build layer1` runs the pack with the `sample` profile (100 wallets and 5 contracts over 5 days), seed 7, and no overlay, then writes the run as one log. Each entity row becomes an `<entity>_created` event at its creation time (no domain names); business events keep their columns. Owners (`[recipe.owners]` in `dataset.toml`): every transaction event (`tx_received`, `tx_included`, `tx_dropped`, `transfer_log`) is keyed on its sender, `from_account`, because the nonce is per sender and a consumer checking nonces or rebuilding a sender's balance needs the sender's receipts, inclusions, drops and transfer logs in one ordered partition (keying on `block` would split a sender's history across blocks; a transfer's receiver gets its credit from the same row); `genesis_allocated` is keyed on the funded `account_id`; `block_produced` has no account and keeps the default partition owner, the one chain shard that builds every block, so the blocks stay in one ordered partition. The pack has no `std` recipes, so there are no internal events.

The designs read the log alone. Simkit's own tables are used only to grade them (the `[[check]]` entries) and to answer the questions (`oracle.sql`).

Facts of this run the designs handle on purpose:

- Account ids in every event (`account_id`, `from_account`, `to_account`) and `tx_id` and `block` are plain integers in the pack, not references, and there is no transactions or blocks entity: a transaction exists only through its events, a block only through `block_produced` and the inclusions and drops that name it.
- All accounts are created at the run's start. Only the 100 wallets get a genesis allocation (2 ETH each) and only wallets send; the 5 contracts are only ever called, with value 0, so they end at balance 0. Transfers go wallet to wallet; 22 are addressed to the sender itself (21 succeed, moving nothing net).
- Every received transaction is resolved exactly once in this run (2,932 included, 64 dropped, none pending at the end of the log); the designs still give an unresolved one the status `pending`.
- Only calls revert (114 of them), and calls carry no value, so in this run "reverted values excluded" changes no balance; the designs still apply the rule (a reverted transaction pays its fee and moves nothing).
- `block_produced` is written only for non-empty blocks, and its `txs` counts dropped transactions too: 58 of the 2,861 blocks only dropped transactions. A block's `block_produced`, inclusions, drops and transfer logs share one event time.

## Designs

All three designs cover the same scope: accounts, genesis allocations, transactions with their whole lifecycle (received, then included as success or reverted, or dropped with a reason, or still pending at the end of the log, and the transfer log of a successful value transfer), and blocks. Nothing is left out: every event of the log is in every design. No entity attribute changes in the log, so no design keeps attribute history: the history here is the transaction's lifecycle, a sequence of events on one key, and each account's balance, a running sum over its genesis, transfers and fees. Every design derives a transaction's status the same way: `success` or `reverted` from its inclusion, `dropped` from its drop, else `pending`; and the value it moved is its value when `success`, else 0. The designs follow the patterns of the *Beyond Facts & Dimensions* atlas.

**`star` — star schema (Kimball).** A static `star_dim_accounts` (kind, creation time) keyed on `account_id` (no SCD2: nothing changes, so a surrogate key would add a lookup and buy nothing). Block is a column, not a dimension: simkit has no blocks table to check one against. One transaction fact per event, at the grain of the event: genesis allocation, transaction receipt (sender, receiver, nonce, value, gas limit, kind), inclusion (block, nonce, gas used, fee, status), drop (block, reason), transfer and block (`txs`, which counts drops too, and `gas_used`). `star_fact_tx_lifecycle` is the accumulating snapshot: one row per transaction with its terms, `received_at`, the `block` and `settled_at` time that resolved it, `included_at` or `dropped_at`, `status` and `drop_reason`, gas used, fee and `transferred_value`. The atlas's verdict holds: the snapshot answers "what became of each transaction, and what did it move" with one scan, at the cost of a row rewritten at inclusion in a live system and of a status rule that lives in the build. Lifecycle facts are exempt from `[[check]]`; every other star table is checked against simkit. No calendar dimension (a date dimension cannot be checked against a simkit table).

**`act` — activity schema.** One stream, `act_account_stream`, with one row per thing that happens to an account, in the standard columns (`activity_id, ts, customer, activity, feature_1, feature_2, feature_3, revenue_impact, link, activity_occurrence, activity_repeated_at`), and the customer table `act_account` (kind, creation time). `customer` is the account, `activity_id` the log's `event_id`, `ts` the event time. The activities and their text features:

| Activity | Event | Customer | `feature_1` | `feature_2` | `feature_3` | `revenue_impact` |
|---|---|---|---|---|---|---|
| `received_genesis` | `genesis_allocated` | `account_id` | — | — | — | +amount |
| `submitted_tx` | `tx_received` | `from_account` | tx_id | kind | value | — |
| `included_tx` | `tx_included`, `status = 'success'` | `from_account` | tx_id | block | gas used | −fee |
| `reverted_tx` | `tx_included`, `status = 'reverted'` | `from_account` | tx_id | block | gas used | −fee |
| `dropped_tx` | `tx_dropped` | `from_account` | tx_id | block | reason | — |
| `sent_value` | `transfer_log` | `from_account` | tx_id | to_account | — | −value |
| `received_value` | `transfer_log` | `to_account` | tx_id | from_account | — | +value |

`revenue_impact` is the signed change to the customer's balance in gwei (null where the balance does not move), so an account's balance at any time is the sum of its `revenue_impact` up to then. A transfer log is two activities, one on each account, that share its `event_id`: the stream's key is (`activity_id`, `activity`), not `activity_id` alone. A block has no account and is not an activity: its number is `feature_2` of every inclusion and drop it settled, which all carry the block's time as `ts`, so the blocks of a day are the distinct `feature_2` of that day's inclusions and drops (a block that only dropped transactions counts), and its gas and fees are sums over its inclusions. A receipt's nonce, receiver and gas limit are not kept (three features are all there is; the receiver of a transfer that moved value is on `sent_value`, and the gas actually used is on the inclusion). `link` is null (no activity has a URL). `activity_occurrence` is the 1-based count of the customer's activities of that kind in `ts` order (ties by `activity_id`), and `activity_repeated_at` the `ts` of the customer's next one, else null. Each activity's keys (and its amount or reason where it is a plain column) are checked against its simkit event table. As the atlas says, one narrow table holds every account's journey and a balance is one `sum` over it; the price is that typed attributes become text features to cast back, one feature slot means different things for different activities (gas used or a drop reason), and a block, which belongs to no customer, has to be reassembled from its transactions.

**`obt` — one big table.** One wide row per fact grain, every attribute bound as of the fact's time (here the creation value, since nothing changes). `obt_transactions` is one row per transaction with its terms, the sender's and receiver's account kinds, the lifecycle flattened into `status`, `drop_reason`, gas used, fee and `transferred_value`, and the block that settled it (number, time, UTC date, its `txs` and gas used). `obt_blocks` is one row per produced block with its UTC date, `txs`, the transactions it included, reverted and dropped, its gas used and fees. `obt_accounts` is one row per account with its kind and genesis allocation (null for contracts). The atlas's trade-off shows: the transaction row is the shape a fraud or fee model reads and every question is one `GROUP BY` or a short union, but each grain repeats what another holds (a block's gas sits on every transaction it settled), and a balance is still a sum across rows, not a column.

## Questions

- **`q1_final_balances`** — every account's balance at the end of the log: genesis plus values received, minus values sent and fees paid; reverted transactions pay their fee and move no value. Needs the lifecycle: the oracle sums transfer logs, but the star and OBT take the value a transaction moved from its final status (and its fee from its inclusion), and the stream sums `revenue_impact`, which is signed for exactly this. Contracts are in the answer, at 0.
- **`q2_daily_chain`** — per UTC day: blocks produced, transactions included (successful or reverted), the gas they used and the fees they paid. It checks that every design keeps every block, including the 58 that only dropped transactions; star and OBT read blocks from their block fact or table, the stream reassembles them from the block numbers on inclusion and drop activities.
- **`q3_drops_by_kind`** — dropped transactions by reason and the sender account's kind, with the number of distinct senders and the value they tried to move. Star and OBT filter the lifecycle on `status = 'dropped'`; the stream must join each `dropped_tx` to the sender's `submitted_tx` with the same `tx_id` for its value.

## Extend

- **More rows:** run the pack with a bigger profile or `--set` (e.g. `uv run datagen run examples/layer1 --profile sample --set wallets=1000`) and make it a new dataset or version with that recipe in `dataset.toml`; a bigger or longer run may leave transactions pending at the end of the log, which every design already handles. Every design and question is written against the log and keeps working.
- **An overlay:** the pack has none yet; an overlay (say, a ring of wallets laundering through contracts, with labels) would be a new dataset, e.g. `datasets/layer1-<overlay>/` with `overlay = ["<overlay>"]`; it adds labels and new actors, so owners and checks may need entries. If it gives calls a value, q1's reverted-value rule starts to matter.
- **A new design:** add its id to `designs` (three per dataset), write `specs/<design>.sql` with `<design>_`-prefixed `-- table:` blocks over the log views, add `[[check]]`s, and an answer file in every question folder.
- **A new question:** a folder under `specs/questions/<id>/` with `oracle.sql` (reads `sim.<table>` only) and one `<design>.sql` per design (reads that design's tables only); all answers must have the same columns and agree with the oracle.
- **A new engine port:** write `engines/<engine>/` from `specs/<design>.sql`. It must read only the log and match `results/` exactly.

Any change to `specs/`, `dataset.toml` or the pack changes the build. Once a version is recorded in `v1.lock.json`, changed output needs a new version (`v2`).
