# entertainment

## What this is

An entertainment agency: agents book entertainers (acts with members and ranked musical styles) for customers (with ranked style preferences), at a contract price for a run of days.

Version `v1`, kind `spider2`. The input is one ordered event log of 306 events; the output is the 13 source tables, rebuilt exactly, and the answers to 3 saved Spider 2.0 questions.

## Raw data

`EntertainmentAgency.sqlite`, 13 tables. The Entertainment Agency sample database from John L. Viescas and Michael J. Hernandez, *SQL Queries for Mere Mortals*: hand-made course data. The licence is unstated; the files ship with the book for its readers.

The 111 engagements run from 2017-09-02 to 2018-03-13, but agents were hired 1997–2000 and entertainers entered 1995–1998: only the activity dates look moved forward by a later edition. Dates are `YYYY-MM-DD` and times `HH:MM:SS` text, read as UTC. Of the 13 tables, 1,348 rows are the four `ztbl*` calendar and number helpers.

The reverse-engineering research, with the queries behind every number, is in [`docs/research/spider2/entertainment.md`](../../docs/research/spider2/entertainment.md).

## How the log was made

Each engagement is an event owned by its customer. Agents, entertainers, members, styles and customers are entities, and so are the three links: an entertainer's members (with a status), an entertainer's ranked styles and a customer's ranked preferences. A link's `ext_id` is its two source ids joined by `/`.

Agents' creation event is `agent_hired`, at `DateHired`, and entertainers' is `entertainer_registered`, at `DateEntered`, the day the agency entered the act on its books. The rest keep `<entity>_created`: their times are rules. Addresses, phones, web pages and e-mails, agents' salary and commission rate, a member's status in an act, and the style-strength and preference ranks can change after creation and the source holds only their value at the extract, so they travel on `<entity>_snapshot` events at N, not on creation.

The four helpers are generated by `specs/build.sql`, not logged: every day from 2017-01-01 to 2020-01-01 (1,096), Sunday-to-Saturday weeks from 2017-01-01 (156), 36 months from January 2017 with their English names, bounds and one-hot month columns, and the numbers 1 to 60. Each matches the source with 0 differing rows. The ranges are constants copied from the source; the engagements imply none of them.

An engagement's end date and stop time travel as text: 17 engagements stop at or after midnight, so an end timestamp would need a rule the source does not state. Salary and contract price are whole dollars (int64); the commission rate is a float carried verbatim.

`uv run dataset build entertainment` runs `specs/ingest.sql` on the read-only source to make a simkit dataset (an internal stage), then writes it as one log. Entity rows become `<entity>_created` events at their creation time; business events keep their columns. The log is in `seq` order: event time, then entities before events at the same instant. Each row's `payload` is a JSON object whose fields are listed in `schema/events.json`.

## Times set by rule

There is no booking or contract date: an engagement is stamped at its performance start, `StartDate` + `StartTime`. Stage 2 has no data to fit a booking lead time. Agents are created at their hire date and entertainers at their entry date, both natural. The rest are rules:
- a member at the earliest entry date of their entertainers;
- an entertainer's member and style links at the entertainer's entry date;
- styles at T0 = 1995-01-20, the earliest natural date;
- a customer, and their preferences, at their first engagement's start; the 2 customers with none at T0;
- snapshots at N = 2018-03-14 00:00, the day after the last engagement ends (EndDate 2018-03-13, StopTime 17:00), so N follows every event and every booked window. Research proposed N = 2018-03-13, the last EndDate; that day is rounded up, since the last engagement ends at 17:00 on it.

## Expected output

`results/` holds every source table, as the source stores it. Each column's type follows the values it holds: text, int64 or float64. A mixed column holds text and numbers together, so it is stored as SQLite's own text rendering and declared in `dataset.toml`.

| Table | Rows | Columns | Mixed columns |
|---|---:|---:|---|
| `Agents` | 9 | 11 | none |
| `Entertainers` | 13 | 11 | none |
| `Members` | 25 | 5 | none |
| `Entertainer_Members` | 40 | 3 | none |
| `Musical_Styles` | 25 | 2 | none |
| `Entertainer_Styles` | 32 | 3 | none |
| `Customers` | 15 | 8 | none |
| `Musical_Preferences` | 36 | 3 | none |
| `Engagements` | 111 | 9 | none |
| `ztblDays` | 1,096 | 1 | none |
| `ztblWeeks` | 156 | 2 | none |
| `ztblMonths` | 36 | 17 | none |
| `ztblSkipLabels` | 60 | 1 | none |

`expected/queries/` holds the answers of the saved questions (`local131`, `local132`, `local133`), computed on the source. `dataset verify` runs `specs/build.sql` over the log, loads the tables into SQLite with the source's DDL, and compares them and the answers exactly: rows as multisets, numbers by value, text byte for byte.

All three questions read only the style tables. local131 counts each style's 1st, 2nd and 3rd preferences; its gold SQL drops the 5 styles nobody prefers and so disagrees with its own CSV, and the saved query is the LEFT JOIN form that reproduces `local131_a` (25 rows). local132 pairs entertainers and customers whose top two styles match in either order: 6 pairs, as `local132_a`. local133 gives each ranked style's distance from the mean weighted score, 4.05: 20 rows, as `local133_a`.

## Regenerate

```bash
uv run refdata fetch                 # once: the Spider 2.0 SQLite files → data/spider2/
uv run dataset build entertainment             # → $NEORISK_DATA_ROOT/entertainment/v1/ (default data/datasets/)
uv run dataset verify entertainment            # exit 0 = every table and answer matches
```

## Extend

- **More rows:** not possible for a fixed source. Stage 2 will generate logs from `specs/pack.py`.
- **A new event type:** declare it in `specs/pack.py`, add its `-- event: <name> owner=<col>` block to `specs/ingest.sql`, and use it in `specs/build.sql`.
- **A new attribute:** add the column to the pack table and to its ingest block. It then appears in the payload and in `schema/events.json`.
- **A new results table:** add it to `specs/source.toml` and a `-- table: <name>` block to `specs/build.sql`.
- **A new saved question:** add `specs/queries/<id>.sql` (SQLite dialect, source table names).
- **A new engine port:** write `engines/<engine>/` from `specs/build.sql`. It must read only the log and match `results/` exactly.
- **Other helper ranges:** a packaging of the file with longer calendars needs new constants in the `ztbl*` blocks of `specs/build.sql`.

Any change to `specs/`, `dataset.toml` or the source changes the build. Once a version is recorded in `v1.lock.json`, changed output needs a new version (`v2`).
